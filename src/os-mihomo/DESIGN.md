# Runtime contract and verification

## Configuration and installation

The independent fork currently validates OPNsense CE 26.7 / FreeBSD 15 amd64; committed recipes define future native targets. One manager controls package boot, rc service actions, configd, UI, subscription cron, WAN changes and watchdog recovery. Root-only state lives in `/var/db/os-mihomo/`, including the generated config, original subscription, settings, merge YAML and runtime home. Packaged GeoIP data and mode presets live in `/usr/local/share/mihomo/`. No new package file or runtime dependency lives under the legacy asynchronous deletion target `/usr/local/etc/mihomo/`.

Fresh installation and unrecognized legacy migration reset transparent activation and start ordinary proxy ports. A private versioned state schema and explicit consent marker preserve transparent policy and administrative Stop during subsequent managed upgrades and reinstalls. Failed activation rolls consent back. Genuine uninstall revokes policy, while desired plugin registration remains for firmware to manage; the GUI unregisters an explicit removal itself. Legacy subscription YAML, URL, dashboard secret and known cron timing survive. Migration extracts only known cron fields from the master configuration, then deletes its temporary migration data. It never creates another master secret-store copy.

Builds require matching native kernel/userland ABI, Python patch version, imported PyYAML and package dependencies. Product annotations match the generated version file, and runtime Python entry points use the target interpreter. Matrix CI uses the target's official signed dependency repository. Every released target needs its own matching native OPNsense lifecycle attestation. Same-ABI series with different dependencies use separate catalogs. The independent repository plugin selects the effective series during firmware configure; the signed readiness checker refuses unavailable or untested targets. The next 27.1 recipe remains disabled until its actual base and validation are available.

Candidates pass through subscription → optional four-key router DNS overlay → local merge YAML → activation gate and enforced invariants → actual core validation. Nonempty mappings deep-merge, empty mappings clear, plain lists/scalars replace, and six prepend/append extensions modify rules, proxies and groups. No script layer executes. Presets select full, TUN-only and proxy-only defaults; per-router controller addresses belong in the merge. Code owns `tun_mihomo`, the stored secret and exclusion of port 53 from every supported listener.

Configuration mutations and watchdog transitions share an advisory lock. Subscription network waits release that lock. A downloaded response is discarded if its URL or device changed during the fetch; other policy changes use their latest values. The core validates private candidates before applying them. Hard-link backups restore source, config, merge and settings on restart failure. Validator diagnostics are captured because they may contain credentials.

## Routing, DNS and recovery

Start restores direct DNS first, then checks the proxy port, actual TUN and installed route before DNS takeover. TUN failure causes startup rejection and rollback. With the DNS scope at all devices, full mode forwards Unbound to the private Mihomo DNS listener after readiness: the helper turns off the system-nameserver forwarding and writes a drop-in root forward zone. That changes the resolver for every client of the router DNS, not only for captured sources, because the request (`dns_requested()`, true only for an effective scope of `all`) reads neither the device policy nor the capture interfaces; bypassed devices, uncaptured interfaces, VPN clients and the router itself, when its system DNS uses Unbound, are all answered by Mihomo. The other scopes never ask for the zone; they are described after the fast TCP path below. A validating resolver is exempt: with Unbound DNSSEC on, the helper writes no journal, leaves forwarding and private addresses unchanged, writes no zone and reports `effective_forwarding` false. Start publishes that answer as `dns_active`, and while the core runs, status adds `dns_note` whenever the request stands but forwarding does not. If DNSSEC is switched on while forwarding is active, the watchdog restores direct DNS once and re-establishes the TUN assignment the restoration releases, retrying that step on its own while status already reports DNS inactive; while a restored backup is pending it removes only the forward zone, as its crash rescue does, and leaves the rest to the next start. Switching DNSSEC off takes effect at the next restart or apply. TUN-only leaves DNS integration disabled. The router DNS switch instead keeps Unbound on its original upstreams and never forwards Unbound back into Mihomo.

The switch supplies exactly nameserver, proxy-server-nameserver, default-nameserver and empty nameserver-policy before the administrator merge. Literal IPv4/IPv6 upstream addresses come from generated DoT configuration, with ownership snapshots recovering temporarily disabled original entries. Host CIDR DIRECT rules and port 853 DIRECT precede administrator and provider rules. A watchdog detects upstream changes and refreshes these pins. A required resolver failure rejects startup; provider fallback must be explicitly removed. Enhanced mode, hijacking and Unbound AAAA policy are not changed by the switch.

The supported client scope is IPv4. An enabled RA/DHCPv6 service with disabled Mihomo IPv6 blocks router DNS activation and causes a visible warning if configured later, unless `ipv6_clients_restricted` declares that captured devices get no IPv6 (below). Full IPv6 validation is a separate deployment task. The plugin adds no AAAA filter of its own, but while the all-devices forwarding is active Mihomo answers every client of the router resolver according to `dns.ipv6`, which follows the IPv6 switch and defaults off, so none of them receive AAAA records for the names Unbound forwards. With the router DNS switch on, or the integration inactive, Unbound's AAAA answers are unchanged; with a captured scope only captured devices' IPv4 queries to the router reach Mihomo, which is why that scope falls back to all devices while captured devices get IPv6 and Mihomo does not carry it.

Auto-route also captures router-originated traffic, including firmware checks, NTP, monitoring and subscription traffic. Review provider rules for their effect on the whole LAN, and scope router exceptions in merge YAML. Preset TUN MTU is 1420 and remains configurable. The bundled FreeBSD core uses FIB 2022; the deployment must provide enough FIBs and gateway reachability in that table. Startup refuses to proceed when the actual TUN route is absent rather than modifying system tunables silently.

Every core crash destroys TUN and its routes, independently of DNS policy. Original Unbound DNS restoration defaults on and is configurable per router. Explicit Stop persists administrative disablement first, stops the core/TUN even if DNS restoration fails, and leaves pending restoration available for retries. WAN events cannot undo Stop. A start syshook runs the idempotent `boot` action because OPNsense never enables `rc.d/mihomo`. Shutdown does not stop the core, so an active forward zone and the disabled system-nameserver forwarding survive a reboot, and until the syshook runs Unbound forwards to a listener that is not up yet. Start restores direct DNS before it renders or validates the configuration, so a configuration that now fails cannot leave the zone behind; the remaining window runs from Unbound's start to the syshook. Within it, forwarded names fail with DNS recovery off, and with it on `forward-first` lets Unbound resolve them itself. Only address events on WAN-like interfaces, the same routing-context flag that excludes them from capture, restart the core, and inet6 events are ignored while Mihomo IPv6 is off. Native Unbound configuration lock/save APIs and configd reload actions are used; ownership records restrict removal to plugin-created interfaces, firewall rules and forwarding entries.

Every Unbound restart `System.dns()` makes follows a change of the configuration Unbound resolves with, in practice of what it forwards, so `drop_resolver_cache()` runs after it. Unless `general/cacheflush` ("Flush DNS Cache during reload") is set, OPNsense 26.7 dumps the cache when it stops Unbound, and `start.sh` loads the dump into the new process in the background, under `/tmp/unbound_start.lock`, after `configctl unbound restart` has returned on the new pid; the configd action `unbound cache flush` only deletes the dump. Issued straight after the restart, as earlier releases did, it landed while the load was still running and never reached the live cache, so records cached under the previous forwarding, such as AAAA that Mihomo withholds, were answered until their TTL ran out. The plugin now waits up to 60 seconds for the start script by taking that lock without blocking and releasing it at once, as OPNsense's stop waits on it (holding it would make a concurrent `flock -n` start skip itself; a path that is not a regular file, such as a FIFO left in `/tmp`, is not waited on), then deletes the dump, so a start that finds no resolver to dump cannot load it, and runs `unbound-control flush_zone .`, which expires every rrset, message and key and also excludes the messages from serve-expired, except with `serve-expired` on and `serve-expired-ttl` at 0: OPNsense accepts that value, and Unbound 1.26's `reply_info_can_answer_expired()` then applies no age limit, so it can still answer a name once with the old message, immediately or when a fresh lookup misses `serve-expired-client-timeout`, before it refreshes it. Neither a failed dump delete nor a failed live flush fails the change: stale answers are the lesser harm, and raising would skip `repair_resolver()` for a restart that left no resolver. A live flush that fails while Unbound runs is logged to `mihomo.log`, since nothing retries it. `repair_resolver()` starts a resolver with none running for the stop to dump, so that start loads whatever dump is left; it empties the cache again once that start is done, which does not depend on the delete having worked. The operator's `cacheflush` is never touched and still governs every other restart. The post-deinstall fallback does the same after the restart it makes when it removes a remnant zone.

The fast TCP path (setting `tcp_redirect`, off by default) exists because sing-tun's gVisor stack sets its TCP send and receive buffers to 20 KiB (`stack_gvisor.go`), which caps each connection at 20 KiB in flight and, through window scale 0, at a 64 KiB receive window. With the setting on, render() appends the listener `{name: opnsense-transparent-tcp, type: redir, port: 7894, listen: 127.0.0.1}` after every merge, reserves its name, and leaves it out when any other listener, port or controller already uses 7894. The bundled core resolves the original destination of a redirected connection with `DIOCNATLOOK` on `/dev/pf`, and its redir listener applies no LAN allow list. The shared routing module emits, per captured interface with IPv4 sources, `no rdr ... to any port 53` and `rdr ... to !<local> -> 127.0.0.1 port 7894` in the same `mihomo` anchor, grouped after all tables and before every filter rule because pfctl refuses translation after filtering. The TUN `match` rules stay byte-identical: after translation the destination is in `<mihomo_local>`, so they skip redirected packets and keep carrying DNS, UDP, IPv6 and any TCP the redirect does not take. `mihomo.inc` registers the anchor as a tail `rdr-anchor`, so port forwards, reflection and captive portal redirects take precedence, and `System.tun()` reloads the filter once when the listener is configured but the hook is missing, since a package upgrade does not reload it.

The rdr carries no `pass`, so the translated packet still meets the administrator's filter rules as TCP to 127.0.0.1:7894. The plugin does not add a quick pass of its own, which would bypass their block rules; a LAN rule with a gateway therefore still matches and sends the redirected SYN toward that gateway, where it is lost, and the documentation asks for a gateway-less pass to 127.0.0.1:7894 above such rules. The routing adapter offers the port only while every listener on it belongs to the running core child (sockstat against the process journal) and the loaded main ruleset contains `rdr-anchor "mihomo" all`; otherwise the anchor holds no translation and TCP stays on the TUN. The port is journaled before the anchor load, so a crash leaves enough state for the next refresh or disable to kill the translated states (`127.0.0.1:7894 (original) <- client`), which would otherwise outlive their rule. Anchor ownership checks `-sn` as well as `-sr`: a translation rule the plugin cannot generate makes enable, refresh and disable fail closed without flushing it, and disable then empties the plugin's source tables so neither the redirect nor the TUN match can select traffic. The watchdog's refresh rewrites the anchor when the listener or hook changes and restores externally flushed translation rules. Adapters that do not opt in (os-sing-box) keep the exact TUN-only anchor text, command trace and status.

The DNS scope (`dns_scope`: `all`, `captured`, `off`) is decided by one function, `effective_dns_scope()` in `dns_scope.py`, which the manager and the routing adapter both import, from the settings, the applied configuration and whether IPv6 reaches captured devices. Only a configuration with the TUN on and Mihomo DNS on `127.0.0.1:1053` answers anybody. Router DNS turns `all` into `off` without changing the stored value, because Unbound would forward to Mihomo and Mihomo back to Unbound, and nothing refuses the combination. `captured` runs as `all` while IPv6 reaches captured devices and Mihomo IPv6 is off, so enabling transparent routing never fails over it; not while Unbound validates DNSSEC, because the helper then declines the zone and `all` would answer nobody while captured devices still got AAAA from Unbound, so `reach_now()` answers no and the record's `ipv6_dnssec` gives the status its note. `ipv6_reaching()` says IPv6 reaches them when config.xml offers clients IPv6 (`advertises_ipv6()`) and an interface transparent routing captures, narrowed by the capture selection as `capture_scope()` narrows the routing context, without WAN-like interfaces, the TUN and loopback, holds a global unicast address (2000::/3 and `is_global`) in `ifconfig -a`; an offer alone, such as the stock 26.7 Dnsmasq IPv6 range on a LAN without a prefix, hands captured devices nothing. Unique local addresses behind NPTv6 or IPv6 outbound NAT, and 6to4 addresses, are not global by that test, so a LAN that reaches the Internet over IPv6 with them reads as not reaching; the README asks for all devices or Mihomo IPv6 there. An unreadable config.xml or ifconfig counts as reaching. A start with transparent routing first has the filter write a missing routing context (`ensure_routing_context()`), which a new installation has none of before its first reload; a context still missing or invalid counts every interface but loopback and the TUN, a superset that answers no only when the router holds no global address at all. Start writes the answer it decided with to the record `dns-scope.json`, with when it last changed, which the adapter and every later status read, so each tick agrees with that start; an unreadable record counts as reaching. A start the watchdog did not hand a confirmed answer keeps a recorded yes against a no it sees (`start_context()`), because one look may catch a WAN reconnect or a boot before the prefix, and restarts the wait from itself, so only the watchdog moves back to `captured`; an answer the configuration's scope does not depend on is recorded as no, so no later start keeps it. `SWITCH_DEFAULTS` fills in `all` for a settings file without the key and `SWITCH_SCHEMA` is not bumped, since re-seeding the switches would turn manual DNS back on; only `initialize()` without settings, legacy data or an upgrade writes `captured`. `settings/set` and backup restore keep the stored value when the key is absent.

The watchdog follows later changes in `follow_ipv6_reach()`, only while the answer can change the running scope (`ipv6_matters()`: a captured choice, router DNS off, the full preset's shape and Mihomo IPv6 off). It looks every 30 seconds, at once when the stat identity of config.xml or of the routing context, which every filter reload rewrites, changes, and on the next tick while a new answer is being confirmed or its wait has ended; config.xml is parsed again only when its identity changes, and ifconfig runs only while the router offers IPv6. `reach_verdict()` needs the new answer on two looks in a row, moves towards `all` at once and back to `captured` no sooner than ten minutes after the last change; leaving an `all` that DNSSEC, switched on at runtime and handed back as in 1.4.1, reduced to nobody is not held back. The change is a restart (`move_dns_scope()`), because both directions change the core's own configuration: the local-name policy exists only for `captured` and would loop under `all`. The new configuration is first rendered and validated while the old core runs (`check_start()`), so one the new scope cannot run changes nothing. Then the journal `dns-scope-move` is written; stop withdraws the redirect and removes the zone before the core stops; start writes the new answer to the record before the core starts, then writes the zone or arms the redirect after the core answers, so the router DNS answers throughout, and crash rescue and the adapter read the same record as for any start. Any successful start removes the journal. A watchdog that finds it left behind restores direct DNS for a stopped core, or restarts a running one to settle the change; while a restored backup is pending the watchdog only rescues and changes no scope. A failed change is rolled back to the previous answer, noted in the record and the status, and retried after `retry_delay()`: a minute towards `all`, at least ten minutes towards `captured`, doubling with each failure in a row up to an hour. If the rollback fails too, the service stays stopped: direct DNS is tried once more, and while it fails the journal stays and the status reports the integration active, so the next ticks keep retrying it; the reason stays in the record (`stopped`) and the status error until a start or a stop. Every change and failure is logged to `mihomo.log`. The newwanip hook ignores IPv6 events while Mihomo IPv6 is off, so nothing else follows a delegated prefix.

`ipv6_clients_restricted` is the administrator's declaration that this router gives IPv6 only to devices transparent routing does not capture; nothing verifies it. It acts only after detection: `advertises_ipv6()` is unchanged and still finds a Dnsmasq range with a constructor in static mode and a Managed radvd entry. `ipv6_restricted()` in `dns_scope.py` reads it as true only when stored as the boolean true. `effective_dns_scope()` then never turns `captured` into `all`, whatever the reach answer, so `ipv6_matters()` is false and the watchdog neither looks nor moves, and the routing adapter, reading the same settings, keeps the redirect even under a record that says reaching. `ipv6_reaching()` answers no without parsing config.xml or running ifconfig, `start_context()` keeps no earlier yes and has the filter write no routing context, and start records no, so turning the declaration on while `captured` runs as `all` returns to `captured` with the restart the save makes. With router DNS, render() no longer refuses an offer Mihomo IPv6 does not carry, and the watchdog no longer publishes its runtime error for one. `restricted_note()` puts the explanation in `dns_note` instead while the service runs and Mihomo IPv6 is off: with router DNS or an effective `captured` scope, when `ipv6_offered()`, cached by the stat identity of config.xml, finds an offer; and, whatever is offered, when the status scope is `all`, because Mihomo then withholds AAAA from the devices the declaration is for. `unbound_validating()`, which the status also asks on every tick of a captured scope, is cached the same way. The page shows the same warning beside the switch, except while the merge YAML sets IPv6, whose value the page does not know; the status note then speaks alone. `SettingsController` reads the posted value with `FILTER_VALIDATE_BOOLEAN`, so a form-encoded "false" is off and anything that is no boolean reaches the backend's refusal. The setting is not in `SWITCH_DEFAULTS`: like `tcp_redirect` it is absent until stored, and absent means off, so an upgrade stores nothing and `SWITCH_SCHEMA` is not bumped. It is in `BACKUP_KEYS` and `Backup.xml`; a restore without it keeps the value the box has, and the controller forwards it only when the post carries it, as it does `dns_scope`.

A captured scope reaches its devices through PF. Behind the `DNS_REDIRECT` flag, which only os-mihomo sets, the shared module adds a `<mihomo_self>` table of the router's own IPv4 host addresses, leaving out loopback, link-local, multicast and the TUN's networks, whose entry `capture_scope()` keeps for this whatever the capture selection (the connected networks in `<mihomo_local>` would also take other resolvers on the LAN), and, per captured interface with IPv4 sources, `rdr on IF inet proto udp|tcp from <mihomo_sources_N> to <mihomo_self> port 53 -> 127.0.0.1 port 1053`. Translation is first match, so both precede the fast path's `no rdr ... to any port 53`, which matches TCP to the router as well; either redirect lays the anchor out as tables, translation, match rules. pfctl prints them with `port = domain`, which `owned_translation_line()` accepts only for an adapter with the flag, and refresh reloads whenever the loaded translation rules differ from the expected ones after normalising that form. A filter reload on 26.7 leaves the anchor loaded. The port is journaled as `dns_redirect_port` before the load. Withdrawal, a port change and disable kill the UDP and TCP states translated to it by id, from one state snapshot, which includes any an administrator's own forward to that port created; arming kills, best effort, the untranslated states from captured sources to the router's addresses on port 53, so a forwarder with a fixed source port moves at once. A foreign translation rule makes enable, refresh and disable fail closed and empties the source and self tables. An enable or refresh that fails before its guarded reload, for any other reason, runs `withdraw_dns_redirect()`: it clears the fingerprint, empties `<mihomo_self>`, drops the redirected states and forgets the port, so the refresh that would have withdrawn a failing core cannot leave captured sources on it; capture and the fast path stay as they were, and the next refresh reloads the anchor in full. os-sing-box has neither the flag nor the hook; its anchor text, command sequence and status are pinned by digest.

The adapter's `dns_redirect_port()` offers 1053 only for an effective `captured` scope with Mihomo DNS on that listener and not fake-ip, only when every UDP and TCP listener on the port (sockstat against the process journal) is the running core child, and only when `/var/run/mihomo-dns-health.json` holds a healthy verdict about that same core, pid and birth, at most 15 seconds old. The manager writes the verdict. `dns_probe.py`, standard library only, asks the core `localhost` over UDP every watchdog tick with a one-second timeout, which its built-in hosts answer without any upstream, and which must get NOERROR or NXDOMAIN: two failures in a row withdraw, three passes re-arm, and a new core is trusted from its first pass. An armed core's first failure is asked again one second later in the same tick, which then skips its upstream round, because a watchdog tick on a busy router lasts well beyond its five-second sleep; a stalled core is withdrawn within one tick. About once a minute, and at once when liveness recovers, it asks a random label under example.com, cloudflare.com and microsoft.com in turn, and asks the router DNS the same name only when Mihomo fails. In those rounds NOERROR and NXDOMAIN are success, a timeout or SERVFAIL failure, anything else no evidence. It withdraws only when, within the three rounds since Mihomo last succeeded, Mihomo failed where the router DNS succeeded under two different zones, and re-arms once Mihomo resolves a probe name again; both failing changes nothing, so a wrong verdict can only send captured devices to the router DNS for a while. The watchdog probes before its routing refresh, so a changed verdict changes the policy and reloads the anchor without restarting the core or touching Unbound; start probes for at most three seconds before the first enable and never fails over it. The router DNS is asked again for a start's unanswered check only in a tick without an upstream round, so no tick probes for more than seven seconds. The verdict file is runtime state under `/var/run`, which a reboot clears, mode 0600, replaced atomically without fsync, removed on Stop and after a crash, and timed with the system-wide monotonic clock. A crash withdraws the redirect with capture whatever `dns_fallback` says, and `restores_direct_dns()` treats a stored `captured` as `dns_fallback` on, both for the helper's `forward-first` and for the crash rescue, so a captured scope running as `all` because IPv6 reaches its devices fails open too while the page hides the switch. Every arm and withdrawal is logged with its reason to `/var/log/mihomo.log`. The rdr carries no pass: an interface rule that does not pass `127.0.0.1` port 1053 without a gateway defeats it, and so does a port forward of port 53, which PF evaluates before the tail rdr-anchor. The status hints at this when captured sources have been active for five minutes without any translated DNS state.

With router DNS off, render() puts `+.name: [127.0.0.1]` entries for the router's local names ahead of every other `nameserver-policy` key, because Mihomo evaluates the policy in order, a run of domain keys as one trie and each rule-set or geosite key alone; a key the merge YAML states keeps its own value. `local_domains()` reads them from config.xml at start and apply: the system domain, Unbound host overrides and their aliases by exact name, Unbound and Dnsmasq forwarding domains, Dnsmasq, Kea and ISC DHCP domains, and the private reverse zones. The entries exist only for an effective `captured` scope, never for `all`, where Unbound forwards to Mihomo and they would loop. Start also asks the router DNS `localhost`; a resolver that does not answer is reported, since it costs local names only, and the watchdog clears the report once it answers.

Status adds `dns_scope` (the effective scope, `all` whenever Unbound forwards), `dns_redirect` (the adapter reports the redirect loaded) and `dns_note`. All three are derived in `publish_status()`, because the backup mirror and the watchdog republish only `dns_active` and `error`; `dns_active` keeps meaning that Unbound forwards to Mihomo, which the crash rescue acts on. The notes cover a preset without Mihomo DNS, router DNS with all devices, the IPv6 fallback and a scope change that is waiting or failed, a paused or waiting redirect, the rule hint, captured devices under DNSSEC, a router DNS that did not answer, and an IPv6 offer the declaration allowed or all devices defeating it.

A core that exits without a stop is restarted by the watchdog. `/var/run/mihomo-restart.json`, runtime state a reboot clears, records whether a start left the core running (`armed`, with the child's pid and birth from the ownership journal, and `kills`, how many kernel kill lines `dmesg` already holds for that pid), the automatic restarts of the last hour on the system-wide monotonic clock the DNS probes use, a pending restart with its reason and due time, whether the last tick could act on the core (`held`), a pause with what met the spent budget (`exit` or `memory`), and the time and reason of the last successful restart. Every `Manager.stop()` disarms the record before anything else, so Stop, remove, suspend, apply, a WAN restart, a scope change and a start that fails never read as an exit. Three stop-and-start cycles nobody asked for are the exception: `wan-restart` from newwanip, the watchdog's re-apply for new router DNS upstreams and `update()`, mostly run from cron. When one of them found the core running and leaves it down, `restart_failed_cycle()` plans a restart through `schedule_restart()` as a detected exit would, with the reason `the restart after a WAN change failed: ...` and its siblings, and republishes the status; the administrator's own Start, Restart and changes fail in front of them and are not retried. A failed start of a WAN restart while the WAN settles was the most likely way to leave an unattended router's proxy down for days; a successful `start()` arms it and ends a pause, and a tick that finds a core running arms it as well, which covers a core that outlived an upgrade. A tick that finds the armed core gone runs the rescue as before and, only once `destroy_tun()` and any required DNS restoration have succeeded, disarms the record, looks in `dmesg` for vm_pageout's `pid N (mihomo), jid J, uid U, was killed: reason` by the recorded pid (a line counts only when the pid has more of them than `kills` recorded at arming, because the message buffer keeps lines for days while pids wrap within hours; the last one gives the reason `killed by the kernel: reason`, otherwise `exited unexpectedly`), and plans the restart 10, 60 or 300 seconds after that tick by how many automatic restarts the rolling hour already holds. A later tick makes it with `_restore_for_start()` and `start()`, the start action's own path, inside the tick's non-blocking hold of the manager lock, which is reentrant for the same manager. The attempt is counted before it is made, so a failed start and a watchdog that dies in one spend the budget too; a failed attempt plans the next on the same ladder, and the fourth within an hour is refused: the record pauses until an administrative start, restart or stop, each of which clears the count, the pause and the note. `restart_blocked()` keeps the core down while the service is disabled without a stop, while `stopped_reason()` holds a scope change whose rollback failed, and while Sing-box owns transparent routing; the backup guard's branch of `watchdog_tick()` never restarts, so an exit there is acted on only once the guard passes. That branch, a failed direct DNS restoration and a failing `destroy_tun()` set `held`, which the next ordinary tick clears; while it is set, `publish_status()` says that a pending restart waits for the reported problem instead of naming a due time that may pass unnoticed, and publishes no `core_memory_limit`, because the memory guard does not run either. A pending restored backup is one of those problems, so the `_restore_for_start()` that `restart_core()` repeats from the start action finds nothing to reconcile. The budget bounds more than log noise: a start that fails after the routing adapter created kernel tables repeats that on every attempt, which is why a failed arm starts no watchdog. `publish_status()` derives `restart_note` and `last_restart` from the record and puts the pending restart's time, its hold or the pause in front of the error (`RESTART_PAUSED` for an exit, `MEMORY_PAUSED` for a core the memory guard found above its limit again, which still runs), so the status action and the backup mirror keep them; every detection, plan, attempt, outcome and pause is logged to `mihomo.log`.

The core starts with `GOMEMLIMIT` at 30% of `hw.physmem`, never below 256 MiB, and without it while the size cannot be read; it is passed in the environment of the daemon(8) call, which hands its environment to the core. Every tick reads the core's resident size once from `kern.proc.pid`, between two ownership checks of the recorded child; each check costs a `sysctl kern.boottime` process, so `Manager.core_usage()` keeps that reading for the rest of the tick, for the status, until a `stop()` or `start()` inside the tick replaces the core: `ki_rssize` in pages at offset 264 of the 1088-byte amd64 `kinfo_proc`, whose `ki_pid` and `ki_start` offsets `process_identity.metadata()` already relies on, so any other layout gives no size. Above half of `hw.physmem` the watchdog stops the core and starts it again through the same `restart_core()`, inside the same budget, so it happens before the kernel has to kill a process for memory. It keeps the exit's ladder from the last attempt, 60 seconds after one recent attempt and 300 after two, logging a wait once, so a core that is above the limit again right after its start does not lose routing and DNS on every tick; with the budget spent it pauses with `memory` and logs that once. Status publishes `core_memory`, null when unknown, and `core_memory_limit`. The guard does not run in the backup guard's branch either.

With the fast TCP path loaded, the watchdog also releases connections the core keeps after their client has gone. Upstream `Relay` in MetaCubeX/mihomo `common/net/sing.go` copies each direction until EOF, half-closes (`closeWrite`) the side that copy wrote to and then waits for the other copy without a deadline, so a pair whose other direction never ends stays open for good. Which copy ended first decides the state of the client socket on `127.0.0.1.7894` and what ends the wait. When the left-to-right copy ends, because the client sent its FIN, Relay half-closes the right side and blocks reading it; a server that never answers a half-close, Google's push port 5228 or a proxy node, keeps it there, while the client socket sits in CLOSE_WAIT and, once the client resets it, CLOSED, which nothing reads any more. `DELETE /connections/{id}` closes the tracked outbound connection, the right side, and the blocked read ends with it. When the right-to-left copy ends first, Relay half-closes the left side, the client acknowledges that FIN, so its socket on the router sits in FIN_WAIT_2, and Relay blocks reading the left side for a FIN the client never sends, typically because it slept or left. DELETE closes the right side and drops the tracker; neither ends a read on the left side, so the left side's socket stays held and is no longer listed. Irvine listed 7927 connections after four days with about 170 alive: 6066 inbound sockets in CLOSED and 1655 in FIN_WAIT_2, 15851 descriptors and 1.6 GB resident; a 4 GB router was killed for memory. A manual DELETE of the 7684 connections whose client socket was CLOSED, or in FIN_WAIT_2 for over an hour, succeeded every time, brought the descriptors from 15829 to 2063 and left every ESTABLISHED client alone; the CLOSED sockets went, but the 1669 in FIN_WAIT_2 stayed, still the core's by sockstat and absent from `GET /connections`, with the core at about 2100 descriptors and 1610 MB resident. Their clients were gone: the Mac behind 345 of them had no FIN_WAIT_2 socket and only 15 in CLOSE_WAIT. `tcpdrop 127.0.0.1 7894 192.168.3.2 57846` printed `127.0.0.1 7894 192.168.3.2 57846: dropped`, the socket went and the core's descriptors fell by 2 at once; dropping all 1672 such sockets one by one took the core from 2167 descriptors to 418, about one each, with routing and the fast path unaffected. About one, because the DELETE had already closed their right sides: it freed two descriptors for each CLOSED pair but one for each FIN_WAIT_2 one, whose left socket the drop then freed. A connection never closed through the controller still holds both sockets, and dropping its client socket frees both. Go kept the resident size, which no cleanup here can return.

`reap_stale_connections()` runs after the routing refresh of an ordinary tick, never in the backup guard's branch, at most once every `STALE_INTERVAL` (60) seconds of the monotonic clock, kept in the watch process's manager, and only while `core_usage()` proves the core and `routing-state.json` reports `tcp_redirect_port` 7894 with transparent routing and `tcp_redirect` on. The TUN path has no kernel socket per connection to consult and is not covered. A scan first reads `GET /connections` through `_proxy_api()`, the client `proxy_tick()` uses, here with a 64 MiB limit instead of 2 MiB, a five-second wait and an `object_pairs_hook` keeping only the keys the scan uses (`CONNECTION_FIELDS`), so a long list is never held whole; then it runs `netstat -an -p tcp` once. Its exit status is not enough: when `net.inet.tcp.pcblist` or the memory for its copy cannot be had, netstat only warns on stderr and exits 0 having printed nothing, which would read as no sockets just when a leaking core has made memory short. So a listing without the listener's own `127.0.0.1.7894` `*.*` `LISTEN` line (`listener_listed()`) fails the scan like a netstat error; a complete one always has it, because the routing helper loads the redirect only after sockstat finds the running core bound there. `listener_sockets()` reads FreeBSD's `a.b.c.d.port` endpoints and keeps, per client endpoint on `127.0.0.1.7894`, the set of its sockets' states, keeping a missing or numeric state as it reads; `fast_path_connections()` keeps TCP from a `Redir` inbound whose reported inbound port, when it is not 0, is 7894, so an administrator's own redir listener is left alone, and reads Mihomo's `null` list as empty. Because the list is read first, every listed connection has its client socket in netstat's output unless the core let go of it meanwhile. `stale_connections()` decides the controller's part per endpoint (`STALE_CLIENT_DONE_STATES`): sockets all CLOSED close every connection on it at once; sockets all in CLOSE_WAIT or CLOSED watch each connection by id, with when it was first seen so and its upload plus download, and close it once `STALE_IDLE` (300) seconds pass with those bytes unchanged, a change restarting the wait; any other state on the endpoint, a new ESTABLISHED socket beside an old CLOSED one from the same client port or a FIN_WAIT_2 socket, holds every connection on it back and forgets its id, as do ids no longer listed. `held_sockets()` decides tcpdrop's part from netstat's output, so it also finds FIN_WAIT_2 sockets no connection is listed for any more, after a DELETE or the core forgetting them: it keeps, per endpoint, when it was first seen in FIN_WAIT_2 and the upload plus download of the connections listed for it then, None while none is, and the endpoint is due once `STALE_IDLE` seconds pass. A listed total that differs restarts the wait, a total listed for an endpoint first seen unlisted included; one that is no longer listed keeps it, since the core then relays nothing on it. An endpoint counts only with FIN_WAIT_2 among its states and nothing but CLOSED beside it (`STALE_HELD_STATES`): `tcp_close()` takes a CLOSED socket out of the lookup hash (`in_pcbdrop()`) and tcpdrop finds its socket through that hash by four-tuple, so the drop can only reach the FIN_WAIT_2 socket, while two states the hash holds cannot share a four-tuple, so such a pair means netstat read the table while it changed and nothing on it is dropped. An endpoint that leaves FIN_WAIT_2 or netstat's output is forgotten and waits from the start if it comes back. No endpoint is both closed and dropped. Every decision is a dictionary lookup, so a scan is linear in the list and in netstat's output; a list of more than 50000 entries is read whole.

Drops go first, while netstat's listing is youngest: tcpdrop names a four-tuple, not the socket netstat listed, so another socket is hit only if a FIN_WAIT_2 socket held for five minutes ends and its client reuses the port within the seconds between the listing and the drop. Closes follow, CLOSED endpoints first. Both share `STALE_CLOSE_BUDGET` (5) seconds, and each kind stops at its own first failure while the other goes on, so a failing tcpdrop never keeps the controller from closing nor the other way round; what is left waits for the next scan, where a socket left over is due again at once, so a backlog does not hold up the tick's other work. `System.drop_redirect_socket()` runs `/usr/sbin/tcpdrop 127.0.0.1 7894 <client address> <client port>` once per socket with a `STALE_DROP_TIMEOUT` (5) second limit, refuses anything but a dotted IPv4 client endpoint, and accepts only exit status 0 together with tcpdrop's own `...: dropped` line for that four-tuple; its error leaves out the four-tuple tcpdrop names in its warning, so a failure reads the same for every socket and is logged once. tcpdrop exits 1 with `tcpdrop: <four-tuple>: No such process` when the kernel's lookup finds no socket (ESRCH from `sysctl_drop()`), which `drop_redirect_socket()` raises as `NoSuchSocketError`: the socket netstat listed ended before the drop reached it, its client having finally sent its FIN or a reset; a backlog, dropped over up to five seconds after one listing, makes that likelier. DELETE never meets this, as Mihomo answers 204 for an unknown id. The scan skips such a socket without counting it, logging it or stopping the drops behind it, and forgets its wait, so a socket on that four-tuple in FIN_WAIT_2 later is a new one and waits from the start. The endpoint is remembered (`vanished`) only while netstat goes on listing it in FIN_WAIT_2; a second miss on it after that new wait means the kernel does not find what netstat shows, which is a failure like any other, logged and tried again at the next scan, so a lookup that never matches cannot pass unseen. tcpdrop rather than a write to `net.inet.tcp.drop` from Python: the sysctl takes two `sockaddr_storage` structures in an order only the C headers define, which ctypes code could get wrong without any test off FreeBSD noticing, while tcpdrop is the base system's own tool and what released the sockets on Irvine; its cost is one process per socket, which the budget bounds. A scan that released something writes one `mihomo.log` line with the counts by reason, the drops as the third, and the core's count, drops included, to `/var/run/mihomo-stale-connections.json`, which names the core by pid and birth; `publish_status()` reads it as `stale_connections_closed`, 0 for any other core, so a new core starts from 0, and null while no core is proven. A new core, and a scan that finds the fast path off, forget the watched ids and endpoints and the missed ones. A failure of the list, netstat, a close or a drop is caught (`STALE_FAILURES`); a scan's failures are logged together, once until a scan has none or they change, and retried at the next scan; they never reach the tick, the crash rescue or the memory guard. A client that half-closes on purpose and then waits more than five minutes for a silent server loses its connection, as does one that keeps its own side open and silent for five minutes after the server has finished.

Both daemon(8) supervisors run with `-H`, so they reopen `/var/log/mihomo.log` on SIGHUP. newsyslog's `R` flag runs `reopen_log.sh`, which calls `mihomo.py reopen-log`; that takes no manager lock, prints nothing on success and exits 0 when nothing runs. A supervisor's kernel title does not show `-H`, so `System.start()` and `watch()` write the supervisor identity of the ownership record they just took to `log-reopen.json` and `watch-log-reopen.json` beside the journals, and `ProcessGroup.reopen_output()` signals only while that marker is private and valid and names the journal's current parent exactly; `send()` proves the process alive and unchanged immediately before the signal. A supervisor started by an earlier release has no marker and is never signalled, because SIGHUP ends a supervisor without `-H` and leaves its child writing into a pipe nobody reads. A marker or journal that cannot be proven exits 1, which newsyslog reports, after the other supervisor was still asked. `mihomo_sub.log` is opened for every line and keeps its line.

The applied configuration is parsed once per version. `_applied_parse()` keys the parse by `(st_dev, st_ino, st_size, st_mtime_ns, st_ctime_ns)` and keeps nothing when that identity changed while the file was read; every writer replaces the file whole, and the change time moves with any rewrite in place, so `apply()` is never answered from a stale parse. On UFS with soft updates the change time of the renamed file settles a few milliseconds after the rename, so the first tick after a rewrite can parse it once more; unchanged ticks after that parse nothing. `applied_config()` hands out a deep copy, and only the DNS shape and the listener check read the cached object itself. A 470 KB configuration of 9480 rules cost the watchdog 0.69 s of CPU to parse on every tick while router DNS was on. That was half of the watchdog's cost: `mirror_backup()` runs on every tick, router DNS or not, and `_mirror_payload()` parsed `subscription.yaml`, as large as the configuration rendered from it, each time; 42 hours of CPU in 8 days on Danika match two 0.69 s parses per 5 s tick. `_source_parsed()` keeps that parse by a SHA-256 of the bytes it just read for the snapshot, so it can never describe other content; `merge_yaml()` copies its base and `_reference_paths()` only reads it. Still per tick, and left for later: the merge and three preset parses (small), gzip and base64 of the subscription, three PHP processes for the backup guard and mirror, `python3 routing.py refresh` with transparent routing, a few `sysctl kern.boottime` processes behind ownership checks, and durable writes of `status.json` and the backup marker. `Loader` stays on the pure-Python parser: libyaml accepts, rejects and reports a few documents differently from it, so `CSafeLoader` cannot be shown to behave the same on every subscription, and with both caches no large document is parsed on an unchanged tick.

## Subscription host source review

Reviewed Passwall-Sub-Panel `main` at commit `4c7b488a8b36ce98579a34624249ec68ac7d60fd`, without sending requests to the live subscription endpoint:

- [Client detection](https://github.com/KazuhaHub/Passwall-Sub-Panel/blob/4c7b488a8b36ce98579a34624249ec68ac7d60fd/internal/pkg/clientdetect/detect.go) lowercases UA and keywords and matches substrings. Families are evaluated in order; the first match wins. Whitelist mode requires a matched, enabled family.
- [Defaults](https://github.com/KazuhaHub/Passwall-Sub-Panel/blob/4c7b488a8b36ce98579a34624249ec68ac7d60fd/internal/adapters/sqlstore/settings_kv_repo.go) put `Clash / mihomo` first, with `clash`, `mihomo`, and `meta` keywords. The proposed UA matches `mihomo`. A dedicated `OPNsense-Mihomo/1` keyword must be ordered before this family to give the fleet separate permissions; a device-specific substring is only needed for per-device policy.
- [Request handling](https://github.com/KazuhaHub/Passwall-Sub-Panel/blob/4c7b488a8b36ce98579a34624249ec68ac7d60fd/internal/transport/http/handler/sub.go) advances blocked-client violations for a valid, accessible user, with a ten-minute deduplication window. Default threshold is 3, configurable globally and by group; reaching it suspends service only when automatic disabling is enabled. Initial blocked-client requests return 403; disabled service and invalid/unavailable tokens return opaque 404.
- [Counter persistence](https://github.com/KazuhaHub/Passwall-Sub-Panel/blob/4c7b488a8b36ce98579a34624249ec68ac7d60fd/internal/adapters/sqlstore/user_repo.go) increments the stored counter without time decay. [Service restoration](https://github.com/KazuhaHub/Passwall-Sub-Panel/blob/4c7b488a8b36ce98579a34624249ec68ac7d60fd/internal/service/user/user.go) clears it when restoring a blocked-client suspension. An allowed request does not reset it.

These are source-level conclusions; deployed panel settings and deployed revision were not probed. The UA's `/1` is a stable format version, independent of package version. Requests retry only timeout/5xx and never 4xx; even 408 and 429 stop immediately. Curl configuration holds the private URL outside process arguments, and no response body or URL is logged.

Its synthetic configuration adapter saves only jail-local XML. Filter/template/configd calls use jail-local adapters: host PF and the production GUI are outside this test's scope. A successful run writes a package-bound test report. The local signer refuses a package changed after that test, then signs the report with its source commit. Legacy packages are retained and catalog-signed but do not inherit the new release's test claim.

Production installation, dashboard authentication, real OPNsense filter/template output and LAN connectivity require a maintenance window. A jail test is evidence for the exercised lifecycle, not certification of those remaining paths. See [deployment](../../DEPLOYMENT.md).
