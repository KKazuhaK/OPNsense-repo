# os-mihomo
原生 OPNsense 配置备份现在包含 Mihomo 设置与凭据、原始订阅和合并 YAML、本地 `type:file` 规则及节点文件、代理组选择和接口/DNS 所有权记录。恢复保留服务启停状态，并关闭透明代理和接管确认；重新接管流量需要在页面明确开启。详见[配置备份与恢复](../../CONFIG-BACKUP.md)。


独立维护的 OPNsense CE Mihomo 插件，当前已验证目标为 26.7 / FreeBSD 15 amd64；构建目标通过配方参数化。

首次安装或未知旧状态迁移只运行普通代理端口，不继承旧包的透明模式。完整订阅 YAML 验证通过后，必须显式启用 TUN；1.1.2 受管理状态建立后的升级及重装保留这一选择和手动 Stop。订阅、secret、定时任务和每台路由器的配置保留在 `/var/db/os-mihomo/`，静态资源与预设位于 `/usr/local/share/mihomo/`，不依赖旧包会延迟删除的目录。

在 **VPN → Proxy Suite** 管理服务、订阅与本地 YAML 合并配置。配置顺序为：完整订阅 → 路由器 DNS 开关覆盖 → 本地 `merge.yaml` → 代码约束与启用守卫 → mihomo 验证 → 事务应用。

映射深度合并，普通值和列表替换；空映射清除已有映射。支持规则、代理组、代理的 `prepend-` / `append-` 六种列表扩展，不执行 JavaScript。三份预设为 `full.yaml`、`tun-only.yaml`、`proxy-only.yaml`。加载预设会替换整个合并文件，先保存自定义内容。初始合并采用完整模式默认值，透明代理仍需显式启用。需凭据访问的 Dashboard 初始绑定所有接口，可在设置中限制为回环地址。TUN 默认 MTU 1420，可按节点传输路径调整。

当前内置 FreeBSD 核心的 TUN 仅支持 `gvisor`。`system` 和 `mixed` 的 TCP 路径会错误地将流量判为广播，因此插件拒绝用这两种栈启用透明代理；启用前选择 gVisor。此限制针对当前内置核心，后续核心需重新验证。

gVisor 协议栈每条 TCP 连接最多只有 20 KB 在途，单条连接的速度约为每个往返 20 KB：即使规则为 `DIRECT`，Wi-Fi 客户端也只有几十 Mbps。“快速 TCP 路径”（默认关闭）改用 PF 重定向，把选中来源的新 IPv4 TCP 交给核心在 `127.0.0.1:7894` 上的监听器，由内核 TCP 协议栈承载；测试环境中 18 ms 往返的单条连接从 TUN 的 8 Mbps 提升到约 1 Gbps。核心仍能取得原始目的地址，规则、嗅探和节点选择不变；连接的入站显示为 `opnsense-transparent-tcp` 而不是 TUN。UDP（含 QUIC）、到 53 端口的 TCP（供 DNS 劫持）和 IPv6 仍走 TUN。只有正在运行的核心确实占有该监听器、且防火墙已加载插件的 `rdr-anchor` 时才启用重定向，否则 TCP 继续走 TUN，状态会显示原因。停止服务或核心退出时会撤销重定向并清除相关连接。防火墙规则看到的被重定向 TCP 目的地址是 `127.0.0.1` 的 7894 端口。按目的主机或端口阻止的规则对被接管的 TCP 不再生效；只放行特定目的主机或端口的规则不再匹配，流量会落入默认阻止；阻止访问防火墙本身的规则会将其阻止。指定网关的 LAN 规则仍会匹配，并把被重定向的连接路由到该网关，连接因此丢失。启用快速路径前，请在这类规则之上放一条不指定网关、放行被接管来源到 `127.0.0.1` 7894 端口 TCP 的规则，或把这些来源排除在接管之外。核心在设备离开后仍保持打开的连接由看门狗关闭，见下文“自动重启、内存与日志”。

设备策略在流量进入 TUN 前按 LAN 源地址选择 TCP/UDP：黑名单中的地址绕过 TUN，白名单只有列出的地址进入 TUN；关闭设备筛选或列表为空时，所有符合接管条件的 LAN 源的 TCP/UDP 进入 TUN。ICMP 及其他控制流量沿用普通路由。绕过的设备沿用现有路由，不经过 Mihomo 的 `DIRECT` 转发。进入 TUN 的流量再遵循订阅和合并规则。用户已有防火墙允许/阻止规则及路由策略仍生效；路由器自身流量和 WAN 入站流量不接管。正常有状态防火墙/NAT 规则下，已建立 DNAT 连接的回包沿用既有状态和正确配置的回程路由。手动配置 HTTP/SOCKS 代理的客户端不受此设备筛选限制。“接管接口”把透明代理限定在选中的内侧接口；留空与旧版本一致，接管所有内侧接口。WAN 类接口永远不会被接管，也不会出现在选项里：接口名为 WAN，或 OPNsense 为它解析出网关，都算 WAN 类，覆盖多 WAN 的每条上行、PPPoE 和带网关的 VPN 出口。网桥请选网桥接口而不是成员口；VPN 服务器需先把隧道分配为接口才能选择。设备策略在选中的接口范围内生效，访问任何本地网络的流量仍然绕过 TUN。

插件关闭核心 `auto-route`，通过独立的源策略选择 LAN 流量，避免用 TUN 路由接管普通路由表中的公网目的地址。独立路由表保留系统的 WAN 和 VPN 路由；复制网关路由时明确保留出接口，支持网关在新路由表中尚不可直接到达的 WireGuard 路由。设备识别依据 IP 地址；请使用稳定地址或 DHCP 保留，并覆盖设备实际使用的全部地址。当前支持范围仍为 IPv4 客户端，IPv6 需要独立端到端验证；私有 jail 的 IPv6 检查不代表客户端端到端支持。部署前验证黑名单、白名单、空列表、用户阻止规则及自定义路由策略；这项修复不代替目标原生环境的验收。

多 WAN 的 DNAT 回程仍由管理员维护，系统中的 WAN 回程路由需正确。插件不重写 NAT、WAN 网关或 `reply-to`；不会修复原本错误的回程配置。需要固定回程 WAN 的连接应有正确的有状态 WAN 规则及 `reply-to`。NAT 内联 **Pass** 跳过后续过滤规则；**Register rule** 的默认回程绑定要求正确的 WAN 网关，且未全局或单条禁用 `reply-to`。详见官方 [NAT 规则关联](https://docs.opnsense.org/manual/nat.html#filter-rule-association)、[WAN 回程规则](https://docs.opnsense.org/manual/firewall.html)和 [Disable reply-to](https://docs.opnsense.org/manual/firewall_settings.html#disable-reply-to)。排查时查看路由、有效 PF 规则和状态，并抓取 WAN、LAN、TUN 的新连接。策略变更后已有连接可继续使用旧状态；必要时仅清除受影响的旧状态，不清空整个状态表。命令与示例见 [DEPLOYMENT.md](../../DEPLOYMENT.md)。

透明模式必须使用返回真实地址的 DNS。默认并推荐 `redir-host`，也支持 `normal`；绕过 TUN 的设备无法依赖 Mihomo 处理 fake-IP 占位地址。透明模式关闭时可以保留旧的 `fake-ip` 选择；启用透明模式或在透明模式下应用配置时，最终生效的 `fake-ip`（包括合并文件覆盖）会自动转换为 `redir-host`，并将该选择保存回设置。共享解析器也必须返回真实地址；已有 fake-IP 缓存可能需要清除或等待过期。

设备策略和“接管接口”只决定数据包的去向。设备向路由器本身查询 DNS 时由谁应答，由另一项设置“DNS 接管范围”（DNS scope）决定：所有设备、仅透明路由接管的设备，或不接管，详见下文。

合并文件不能改变 `tun_mihomo` 设备名、覆盖持久化 secret、让任何监听器占用 53，或绕过透明模式的启用守卫与真实 DNS 约束。路由器 DNS 只与监听 `127.0.0.1:1053` 的 Mihomo DNS 集成，自定义监听器由管理员管理。

**哪些设备由 Mihomo 应答 DNS。**“DNS 接管范围”（设置项 `dns_scope`，位于 DNS 页“通过路由器 DNS 解析”旁边）决定设备向路由器本身查询 DNS 时，哪些由 Mihomo 应答。只有透明路由运行的配置同时开启 TUN、且 Mihomo DNS 监听 `127.0.0.1:1053` 时它才起作用，即完整预设，或保留其 DNS 的合并 YAML。TUN-only 预设不通过路由器应答任何设备，状态会说明原因；proxy-only 预设根本没有透明路由。无论哪种范围，“接管客户端 DNS”开启时，被接管设备发往其他解析器的 DNS 仍在 TUN 内由 Mihomo 应答；加密 DNS（DoH、DoT、DoQ）永远不会被重定向。

| 范围 | 取值 | 向路由器 DNS 查询时由 Mihomo 应答的设备 | Unbound |
|---|---|---|---|
| 所有设备（All devices） | `all` | 路由器解析器的所有客户端 | 根域转发给 Mihomo |
| 仅透明路由接管的设备（Only devices captured by transparent routing） | `captured` | 透明路由接管的 IPv4 来源，查询路由器任一 IPv4 地址，UDP 和 TCP 都算 | 不改动 |
| 不接管（No devices） | `off` | 无 | 不改动 |

**默认值。**升级保持原有行为：没有该字段的设置文件按 `all` 处理，从旧脚本升级的安装也一样。全新安装默认 `captured`，只有在被接管设备确实拿到 IPv6 地址时才按“所有设备”运行（见下文关于 IPv6 的说明）。恢复在该设置出现之前做的配置备份时，保留路由器当前的范围；`settings/set` API 调用不带 `dns_scope` 时保留已存储的值，`ipv6_clients_restricted` 也一样（见下文“仅向未接管设备提供 IPv6”）。其他字段目前还没有这种处理，所以 API 客户端仍应提交读取到的完整 payload。

**所有设备**即以往所有版本的行为。这项集成改动的是整个解析器，而不是某些客户端的路径：它关闭“使用系统 DNS 服务器”（Use System Nameservers），并为根域写入一个 drop-in 转发区，凡是 Unbound 不从本地数据或更具体的转发区应答的查询都交给 Mihomo。此时所有使用路由器 DNS 的客户端都由 Mihomo 应答，包括被设备策略绕过的设备、未选中的接口、VPN 客户端、Pi-hole 等下游解析器，以及系统 DNS 使用 Unbound 时的路由器自身。Unbound 开启 DNSSEC 验证时完全不应用这项集成，因为 Mihomo 的应答不带签名：Unbound 的配置和上游保持原样，状态显示 DNS 集成关闭并说明原因，Mihomo 只应答在隧道内劫持到的 DNS。集成生效期间开启 DNSSEC，看门狗会把 Unbound 交还给原有上游一次；关闭 DNSSEC 则在服务下次重启或应用配置时生效。开启“通过路由器 DNS 解析”时，Unbound 转发给 Mihomo、Mihomo 又查询 Unbound，会形成循环，所以“所有设备”按不接管处理，已存储的选择不变；页面会把这一项置灰并说明原因。

**仅透明路由接管的设备**不改动 Unbound。每个有 IPv4 来源的被接管接口，都会在插件的 `mihomo` anchor 中得到一条 UDP 和一条 TCP 的 `rdr` 规则：来自被接管来源、发往路由器自身 IPv4 地址表的 53 端口查询，被转到 `127.0.0.1` 的 1053 端口；这两条规则排在快速 TCP 路径的规则之前。来源与透明路由接管的来源完全一致，即“接管接口”范围内的设备策略：黑名单排除列出的设备，空白名单等于全部设备。其他设备、未被接管的接口、未分配为接口的 VPN 隧道上的客户端，以及路由器自身，继续使用路由器 DNS，也照常拿到 AAAA 记录。只有同时满足以下条件才会布设重定向：正在运行的核心同时占有该端口的 UDP 和 TCP 监听，防火墙已加载插件的 `rdr-anchor`，且看门狗对同一核心的最近一次探测（不超过 15 秒）判定它能应答。在此之前被接管设备使用路由器 DNS，状态显示“已暂停”（Paused），附注说明重定向正在等待。

防火墙看到的被重定向查询是发往 `127.0.0.1` 1053 端口的 UDP 或 TCP；插件不添加会绕过管理员规则的放行规则。默认的 LAN 规则会放行它。只放行“到 This Firewall 的 DNS”的规则、阻止访问防火墙本身的规则，或指定网关的规则，会把它丢弃或送往那个网关：请在这类规则之上放一条不指定网关、放行被接管来源到 `127.0.0.1` 1053 端口 TCP 和 UDP 的规则，或把该接口排除在接管之外。被接管接口上的 53 端口转发优先生效，因为插件的 `rdr-anchor` 最后才被评估，重定向根本看不到这些查询。探测走回环地址，看不到上述两种情况；如果被接管来源持续活动 5 分钟、却没有任何 DNS 到达 Mihomo，状态会给出提示。被接管设备使用其他解析器（例如 DoH，或 DHCP 下发的公共 DNS）时也会出现同样的提示，此时可以忽略。强制门户对未认证客户端的规则也可能因此不再匹配，请把门户接口排除在接管之外。这种范围不支持 CARP 和 pfsync。

被接管设备不再经过 Unbound，所以 Unbound 的拦截列表、访问控制和按客户端统计对它们不再生效，本地名称也一样。因此在“通过路由器 DNS 解析”关闭时，插件在 Mihomo 的 `nameserver-policy` 最前面写入一组条目，把路由器自己的名称交回路由器 DNS（`127.0.0.1` 的 53 端口）：系统域；Unbound 主机覆盖及其别名（按完整名称）；Unbound 或 Dnsmasq 转发给其他服务器的域；Dnsmasq、Kea 和 ISC DHCP 分发或登记的域；以及 RFC 1918、链路本地、唯一本地地址的反向区和 `home.arpa`。公共的反向查询仍由 Mihomo 处理。这些名称在服务启动或应用配置时读取，之后新增的域要到下一次重启才生效。合并 YAML 的 `nameserver-policy` 里写了同名键时，以合并 YAML 的值为准。“所有设备”下绝不生成这些条目：那时 Unbound 转发给 Mihomo，会形成循环。启动时路由器 DNS 不应答，状态会说明本地名称在它恢复前无法解析。同时开启“通过路由器 DNS 解析”是保留拦截列表和本地名称最简单的办法：Mihomo 的所有查询都交给路由器 DNS，被接管设备仍由 Mihomo 应答，也不会形成循环。

Unbound 开启 DNSSEC 验证时仍允许“仅透明路由接管的设备”：其他设备继续由 Unbound 验证，状态会注明被接管设备向路由器 DNS 查询时由 Mihomo 应答、不经验证。

重定向与接管一样只做 IPv4。被接管设备在 Mihomo IPv6 关闭时拿到 IPv6 地址，就会从路由器 DNS 拿到 AAAA 记录，并通过 IPv6 绕过隧道；因此这时范围自动按“所有设备”运行，与以往版本相同，状态会说明原因，透明路由的启用不会因此失败。判断条件是：路由器向客户端提供 IPv6（radvd、track6 的自动 RA、Dnsmasq 的 IPv6 地址池、Kea DHCPv6 或 DHCPv6 中继），并且透明路由接管的某个接口持有全局 IPv6 地址。链路本地、唯一本地和 WAN 地址不算；所以 OPNsense 26.7 的默认安装虽然带有 Dnsmasq 的 IPv6 地址池，但在前缀到达 LAN 之前发不出任何地址，只由 Mihomo 应答被接管设备。LAN 不用全局地址也能经 IPv6 上网时（使用唯一本地地址并经 NPTv6 或 IPv6 出站 NAT，或使用 6to4 地址），插件识别不出来：这时请手动选择“所有设备”，或开启 Mihomo IPv6。看门狗会自动跟随变化，通过重启服务切换范围，代理连接会因此重置：前缀到达后约 40 秒内切到“所有设备”，切回“仅透明路由接管的设备”每 10 分钟最多一次。重启服务或开机不会自行切回，所以 WAN 重连时前缀还没回来也保持“所有设备”。每次切换都记入 `mihomo.log`。Unbound 开启 DNSSEC 验证时，“所有设备”不会应答任何设备，所以范围保持“仅透明路由接管的设备”，状态会提醒被接管设备经 IPv6 向路由器 DNS 查询时可能拿到 IPv6 应答。开启“仅向未接管设备提供 IPv6”时，以上都不会发生。

为“所有设备”写入或移除根域转发区都会重启 Unbound，与 1.4.x 相同：选择范围时；“仅透明路由接管的设备”因被接管设备拿到 IPv6 而开始或停止按“所有设备”运行时，无论发生在启动时还是由看门狗切换；以及“所有设备”生效期间启动或停止服务、核心崩溃后看门狗移除转发区时。重启需要几秒钟，其间到达的查询可能有一次得不到应答，直到客户端重试。每次这样的重启之后，插件都会清空 Unbound 的缓存，不论“重载时清空 DNS 缓存”（Flush DNS Cache during reload）如何设置，因为否则 OPNsense 会把缓存重新载入重启后的解析器：按旧方式解析得到的应答，例如 Mihomo 不提供的 AAAA 记录，会一直返回到 TTL 过期，默认最长一天。之后各域名在客户端查询时重新解析。该设置本身不会被修改，其他 Unbound 重启仍按它处理。缓存无法清空时，`mihomo.log` 会记录下来。开启“提供过期应答”（Serve Expired Responses）并把“过期应答的 TTL”（TTL for Expired Responses）设为 0 时，Unbound 可以返回任意久之前过期的应答，某个域名在重新解析期间仍可能有一次得到旧应答。

出现任何故障都会撤回重定向，被接管设备回到路由器 DNS，与“退出时恢复直连 DNS”（Restore direct DNS on exit）的设置无关；该设置只作用于“所有设备”，其他范围下页面会隐藏它。“仅透明路由接管的设备”因被接管设备拿到 IPv6 而按“所有设备”运行时，核心崩溃后 Unbound 同样会回到自己的上游，与该设置无关。看门狗每隔几秒向 Mihomo 查询一次 `localhost`（Mihomo 不经任何上游即可应答）；已布设的核心没有应答时，一秒后再查询一次，第二次仍失败就撤回重定向。这项查询必须得到 NOERROR 或 NXDOMAIN，其他应答（包括 REFUSED）都算失败。看门狗还约每分钟一次查询 example.com、cloudflare.com 或 microsoft.com 下的随机名称，只在 Mihomo 失败时才向路由器 DNS 查询同一名称；这里 NXDOMAIN 和空应答都算成功，只有超时和 SERVFAIL 算失败，其他应答不作为依据。误判最坏只会让被接管设备暂时改用路由器 DNS。撤回时会清除被重定向的状态，包括管理员自己转发到 `127.0.0.1` 1053 端口所产生的状态；布设时会清除被接管来源此前发往路由器 53 端口的状态，使固定源端口的转发器立即切换过来。

| 核心崩溃 | 看门狗在下一个 tick 连同接管一起撤回重定向，并清除其状态 | 约 5 秒；10 秒后看门狗自动重启核心，重定向随之重新布设（见下文“自动重启、内存与日志”） |

|---|---|---|

降级到 1.4.x 时，旧包 suspend 服务会撤回重定向；此后只要“通过路由器 DNS 解析”关闭且使用完整预设，1.4.x 会重新让 Mihomo 应答所有设备。

“通过路由器 DNS 解析”默认关闭。开关本身仅覆盖 nameserver、proxy-server-nameserver、default-nameserver、nameserver-policy 四项，不改变 DNS 劫持或 Unbound 的 AAAA 策略；透明模式另行强制真实 DNS。根据本机 DoT 配置为 IPv4/IPv6 上游地址和 853 端口注入优先 DIRECT 规则，上游改变时自动刷新，避免节点解析死锁。开启该模式时 Unbound 不会再转发给 Mihomo：“所有设备”按不接管处理，所有未被接管的设备都继续使用 Unbound 的上游。“仅透明路由接管的设备”仍然可用，而且是推荐的组合：被接管设备由 Mihomo 应答，Mihomo 再向路由器 DNS 查询，本地名称和拦截列表都保留。必须移除订阅的 DNS fallback，上游不可用时明确失败。

手动 DNS 字段使用 Mihomo URL 语法。“覆盖订阅 DNS”开关明确控制非空手动字段是否替换运行配置中的对应项目；关闭后立即恢复订阅 DNS，同时保留手动值供以后启用。订阅 YAML 原文件始终不会被改写，启用路由器 DNS 时则以路由器 DNS 为优先。Mihomo 把 `#` 后的第一个值解释为代理或接口，而 Unbound 的 `IP@端口#主机名` 用它表示 TLS 校验名。为避免复制后直到运行时才出现 `interface not found`，插件会把 Nameservers 和节点 DNS 中的 `tls://IP#长主机名` 规范化为 `tls://长主机名`；`#vtnet1`、`#RULES` 等接口或规则选择保持原样。Bootstrap 仍必须是字面 IP，因此复制来的同类写法会在该字段保存为其中的 IP，由规范化后的主机名字段执行加密查询，避免形成解析依赖环。

当前发布范围是 IPv4 客户端。选择“通过路由器 DNS 解析”时，若 RA/DHCPv6 已向客户端提供 IPv6，而 Mihomo IPv6 关闭，插件拒绝启用；运行中出现这种变化会提示；开启“仅向未接管设备提供 IPv6”时除外。检测覆盖 OPNsense 26.7 的 radvd 条目与 track6 自动 RA、Dnsmasq 的 IPv6 地址池、Kea DHCPv6 和指向 IPv6 服务器的 DHCP 中继；仅开启 Dnsmasq 全局 RA 开关或使用 identity association 不算提供 IPv6。选择“通过路由器 DNS 解析”时，插件不抑制 AAAA。路由器 DNS 关闭且 DNS 接管范围为“所有设备”时，Mihomo 按其 IPv6 开关应答（默认关闭），所有使用路由器 DNS 的客户端都拿不到 Unbound 转发给 Mihomo 的域名的 AAAA 记录，未被接管的客户端也一样。范围为“仅透明路由接管的设备”时，Mihomo 只应答这些设备发往路由器的 IPv4 查询；被接管设备拿到 Mihomo 不承载的 IPv6 地址时，范围按“所有设备”运行（见上文）。插件从不修改 RA/DHCPv6；Mihomo IPv6 关闭时，原生 IPv6 流量绕过 TUN。未来启用客户端 IPv6 代理应完成独立端到端验证。

**仅向未接管设备提供 IPv6。**“仅向未接管设备提供 IPv6”（IPv6 only for uncaptured devices，设置项 `ipv6_clients_restricted`，位于 DNS 页“DNS 接管范围”下方，默认关闭）是管理员的承诺：本路由器只把 IPv6 发给透明路由不接管的指定设备（例如需要通过 IPv6 访问的 NAS），被接管设备一律拿不到 IPv6。插件不会核实这一点。开启且 Mihomo IPv6 关闭时，IPv6 下发不再阻止“通过路由器 DNS 解析”启用，看门狗也不再为此报运行错误；范围“仅透明路由接管的设备”也不再退回“所有设备”，看门狗既不检查接口，也不为此重启服务。检测本身不变，状态会注明检测到了 IPv6 下发、并按管理员的声明放行。关闭时的行为与没有这项设置完全相同；Mihomo IPv6 开启时它不起任何作用。升级、恢复不含该字段的备份、`settings/set` 不带该字段，都保留已存储的值；没有存储值即为关闭。

**风险。**被接管设备不拿到 IPv6，全靠这项承诺。被接管设备如果仍拿到了全局 IPv6 地址，就能在隧道之外直接访问 IPv6 目的地，并经 IPv6 从路由器 DNS 拿到 AAAA 记录，绕过代理。

**与 DNS 接管范围的搭配。**这项声明适合与“通过路由器 DNS 解析”一起使用，或者搭配“仅透明路由接管的设备”“不接管”两种范围。范围为“所有设备”且路由器 DNS 关闭时，Mihomo 按关闭的 IPv6 开关应答所有设备，拿到 IPv6 的设备同样从路由器 DNS 拿不到 AAAA 记录，经路由器 DNS 按域名访问时只会走 IPv4；页面会在开关旁提醒，状态也会说明。

**推荐的 OPNsense 26.7 配置**，以 LAN 跟踪运营商 DHCPv6-PD 下发的前缀、只给一台 NAS 提供 IPv6 为例：

1. 让 NAS 不被接管：加入黑名单、不列入白名单，或放在“接管接口”之外的接口上。
2. 在 **Services > Router Advertisements** 为 LAN 添加一条 **Managed** 模式的条目，设备只能通过 DHCPv6 获得地址，不能通过 SLAAC 自行配置；并取消该条目高级选项中的 **Enable DNS**，不向任何设备通告 IPv6 解析器，NAS 仍可经 IPv4 从路由器 DNS 拿到 AAAA 记录。该条目会取代跟踪前缀的 LAN 的自动 RA；自动 RA 与 Assisted、Stateless、Unmanaged 一样，会让所有设备自行配置地址。
3. 在 Dnsmasq 中删除透明路由接管的接口上的其他所有 IPv6 地址池，包括默认自带、`slaac` 模式的 `::1000` 至 `::2000` 地址池，并关闭常规设置中的 **Router advertisements** 开关，让 Managed 条目成为唯一的 RA 来源。然后为 LAN 添加一个 IPv6 地址池，Constructor 选 LAN，Mode 选 **Static**（只服务预留），不选 RA 模式；再按 NAS 的 MAC 地址预留，后缀例如 `::4`。这些接口上也不能有 Kea 或 ISC 的 DHCPv6 服务。
4. LAN 上只放行该主机的 IPv6，例如用 LAN 前缀加同一后缀的 Dynamic IPv6 Host 别名（前缀变化时自动跟随），并阻止从 LAN 进入的其他所有 IPv6，不论源地址是什么，发往防火墙自身地址的也包括在内；OPNsense 为邻居发现和 DHCPv6 自动生成的规则仍然优先生效。

这样，没有预留的设备既拿不到可用的 IPv6 地址，也无法经 IPv6 访问路由器 DNS。插件本身从不配置 RA、DHCPv6 或防火墙规则。

核心异常退出后清除插件的透明接管策略和 TUN 路由，被接管设备的 DNS 重定向也随之撤回；默认自动恢复原有直连 DNS（只有“所有设备”范围需要），每台可配置。显式 Stop 即使 DNS 恢复失败也停止核心和透明接管，随后重试 DNS 恢复。WAN 事件和看门狗都不会重新启动手动停止的服务；没有经过 Stop 就退出的核心由看门狗重新启动，见下文。除非被手动停止，服务会在开机时启动：OPNsense 从不直接运行 `rc.d/mihomo`，因此由启动钩子负责。关机不会停止核心，所以生效中的“所有设备”DNS 集成会保留到重启之后（被接管设备的重定向只存在于运行中的防火墙，不会保留），启动钩子运行前 Unbound 会转发到尚未监听的端口；开机启动在渲染和验证配置之前先恢复直连 DNS，剩下的是 Unbound 启动后几秒钟的窗口。在这段窗口内，若关闭了自动恢复直连 DNS，Unbound 转发的域名无法解析；若开启，Unbound 会改为自行解析。只有 WAN 类接口的地址变化才会重启核心，Mihomo IPv6 关闭时忽略 IPv6 续约，DHCPv6 续约不再中断已代理的连接。关闭透明模式仅清除插件创建的接口、策略和路由，不清空防火墙状态表。

启动时在本机记录核心写入的系统 DNS 指纹。异常退出后通过 OPNsense 原生 DNS 重载恢复系统解析，失败会重试；用户后来修改的解析文件或显式配置的 DNS 不会被覆盖。这份临时恢复记录不进入 XML 备份。

**自动重启、内存与日志。**核心没有经过 Stop 就退出时（程序崩溃，或路由器内存耗尽时被内核杀掉），看门狗先按上文完成救援：撤回路由，并在需要时恢复直连 DNS。救援成功后，看门狗通过与“启动”按钮完全相同的路径重新启动核心，因此透明路由、快速 TCP 路径以及 DNS 接管范围对应的转发区或重定向，都与手动启动后完全一致。第一次自动重启在看门狗发现退出 10 秒后进行，紧接着的第二次在 60 秒后，之后每次在 300 秒后；启动失败也算一次，并按同样的间隔重试。任意 60 分钟内最多自动重启三次；超过后看门狗停止尝试，状态错误会写明 `Mihomo exited repeatedly; automatic restart is paused after 3 restarts within an hour. Start resumes it.`（Mihomo 反复退出，一小时内重启三次后暂停自动重启，点击“启动”恢复。）`mihomo.log` 则把暂停与触发它的事件记在同一行，例如 `Mihomo stopped (exited unexpectedly); automatic restart is paused after 3 restarts within an hour. Start resumes it.`。“启动”“重启”“停止”都会清零计数。

以下情况不会自动重启：手动 Stop 之后；插件升级或卸载时的停止之后；Sing-box 占用透明路由时；DNS 接管范围切换的回滚失败、服务因此保持停止时。WAN 地址变化后的重启、订阅更新（无论是否定时）后的重启，或看门狗因路由器 DNS 上游变化而重新应用配置时的重启，如果启动失败，核心就在没有人要求的情况下停着，因此按退出处理：按同样的间隔重试，并计入同样的每小时三次额度。管理员自己的“启动”“重启”或修改设置失败时，会直接报告给管理员，不会自动重试。

有已恢复的配置备份待应用，或已保存的备份被修改、等待修复时，看门狗只救援路由和 DNS：在 Stop、完成恢复或修复、或重启路由器之前，既不自动重启核心，也不做内存保护。到期的自动重启会等待；退出后的路由清理持续失败时同样等待。这时状态不再给出重启时间，而是说明自动重启在等待所报告的问题解决。

看门狗会按退出核心的 PID 在内核消息缓冲区（`dmesg`）中查找原因，只认该核心启动之后写入的记录，因为缓冲区会保留数天，而 PID 几小时内就会重复使用：如果是被内核杀掉，日志和状态会写明，例如 `killed by the kernel: failed to reclaim memory`；否则写 `exited unexpectedly`。每次发现退出、安排重启、尝试、失败和暂停都记入 `mihomo.log`。服务状态旁会显示看门狗上一次自动重启核心的时间和原因，直到下一次“启动”“重启”或“停止”。计数保存在 `/var/run/mihomo-restart.json`，路由器重启会清除它，开机时核心照常启动。

**内存。**核心启动时设置 Go 的软内存上限 `GOMEMLIMIT`，为物理内存（`hw.physmem`）的 30%，不低于 256 MiB，使垃圾回收在核心占满路由器其余内存之前更积极地回收。除上文所述备份待处理的情况外，看门狗每个 tick 还会读取核心的常驻内存：超过物理内存的一半时记入日志，并以受控方式重启核心，计入同样的每小时三次额度，间隔也相同：自动重启后不久又超过上限的核心，要等到那次重启 60 秒后才再次重启，第二次之后则等 300 秒。这一切都赶在内核因内存不足而杀进程之前。状态会显示核心内存和这个上限，例如 `Core memory: 171 MB (restarted above 2.0 GB)`。如果核心确实需要超过一半的路由器内存，它会被重启到额度用完，之后保持运行，状态错误写明 `Mihomo went above its memory restart limit again; automatic restart is paused after 3 restarts within an hour. Start resumes it.`（核心再次超过内存重启上限，一小时内重启三次后暂停自动重启，点击“启动”恢复。）请给路由器增加内存，或减少订阅中的规则和 provider。

**残留连接。**开启快速 TCP 路径时，核心可能在设备早已离开后仍保持连接打开。Mihomo 分别转发连接的两个方向，一个方向结束后，把结束以半关闭（half-close）的形式转给另一端，然后不限时地等待另一个方向也结束；另一个方向始终不结束的连接会让两端的套接字一直打开。两个方向都会出现这种情况，各自需要不同的处理：

- 设备先发送完毕。Mihomo 对服务器一侧做半关闭并等待服务器结束，而不回应半关闭的服务器（例如 Google 推送服务的 5228 端口，或某些代理节点）永远不会结束。设备在路由器上的套接字停在 `CLOSE_WAIT`，设备重置连接后变为 `CLOSED`，再也没有人读取。通过 Mihomo 的控制器关闭这条连接，会关闭 Mihomo 正在等待的服务器一侧，连接随之结束。
- 服务器先结束。Mihomo 对设备一侧做半关闭并等待设备发送完毕，而已经休眠或离开网络的设备永远不会发送完毕。设备的套接字停在 `FIN_WAIT_2`。通过控制器关闭连接无法结束这种等待：服务器一侧会被关闭，控制器也不再列出这条连接，但 Mihomo 仍在等待设备的套接字，它仍保持打开，只是再也看不到。只有用 FreeBSD 的 `tcpdrop` 在路由器内核中丢弃设备的套接字，才能结束它。

一台路由器运行四天后积累了 7927 条连接，其中只有约 170 条仍然有效，打开的文件描述符约 15800 个，核心内存从 160 MB 涨到 1.6 GB；另一台 4 GB 内存的路由器因内存不足被内核杀掉。在第一台上，通过控制器关闭残留连接释放了设备套接字为 `CLOSED` 的连接，文件描述符降到约 2100 个，但留下约 1670 个处于 `FIN_WAIT_2` 的设备套接字，仍被占用且不再列出；用 `tcpdrop` 丢弃它们之后，核心的文件描述符从 2167 个降到 418 个，路由和快速 TCP 路径都未受影响。

现在看门狗每分钟一次通过控制器列出核心的连接，并用 `netstat` 列出内核中 `127.0.0.1` 7894 端口上的套接字。经快速 TCP 路径进入的连接，在设备一侧的套接字为 `CLOSED`，或为 `CLOSE_WAIT` 且连续 5 分钟两个方向都没有传输任何数据时，通过控制器关闭。设备一侧的套接字连续 5 分钟处于 `FIN_WAIT_2`，且控制器为它列出的连接（如果仍有列出）在此期间没有传输任何数据时，用 `tcpdrop` 丢弃；控制器已不再列出的套接字也会被丢弃，例如此前通过控制器关闭后遗留的套接字。`ESTABLISHED` 或其他任何状态的套接字都不会被触碰，监听器自身（`127.0.0.1` 7894 端口）以外的套接字、经 TUN 进入的连接和 UDP 也一样。每次关闭了连接的扫描在 `mihomo.log` 中记一行，按原因分别计数，例如 `Closed 14 stale connections of the fast TCP path (11 whose client had closed, 1 half-closed and idle for 5 minutes, 2 held open by a client that never closed).`；控制器、`netstat` 或 `tcpdrop` 没有按预期应答而失败的扫描只记一次，一分钟后重试。状态会在核心内存旁显示本次核心启动以来关闭的数量（包括丢弃的套接字），例如 `Stale connections closed: 7684`（已关闭的残留连接数）；新启动的核心从 0 重新计数。这只覆盖快速 TCP 路径：TUN 承载的连接在路由器内核中没有自己的套接字可供比对，那里仍只能依靠上文的内存上限。设备有意半关闭连接后，又等待一个不发送任何数据的服务器超过 5 分钟时，这条连接会被关闭；服务器结束后，设备保持自己一侧打开、却超过 5 分钟不发送任何数据时，也一样。

**日志。**核心和看门狗通过 daemon(8) 的监督进程写入 `/var/log/mihomo.log`，这些进程一直打开着该文件。现在它们以 `-H` 启动；newsyslog 轮转该文件时（达到 1 MB，保留五份）会运行 `/usr/local/opnsense/scripts/mihomo/reopen_log.sh`，向本版本记录为带 `-H` 启动、且经核实正在运行的每个监督进程发送 SIGHUP，二者随即重新打开新文件。以前的版本中两者会继续写入已轮转的文件，第一次轮转之后的日志全部丢失。旧版本启动的监督进程不会收到信号，因为 SIGHUP 会让它退出；升级会重启这两个进程。`mihomo_sub.log` 每写一行都重新打开，轮转无需额外处理。
