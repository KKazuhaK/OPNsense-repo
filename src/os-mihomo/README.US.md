# os-mihomo
Native OPNsense configuration backups include Mihomo settings and credentials, the original subscription and merge YAML, local `type:file` rule and proxy-provider files, proxy-group choices, and interface/DNS ownership journals. Restore preserves the service enabled state and turns transparent routing and consent off; the operator explicitly enables transparent routing again. See [configuration backup and restore](../../CONFIG-BACKUP.md).


An independently maintained Mihomo integration for OPNsense CE, currently validated on 26.7 / FreeBSD 15 amd64. Committed recipes parameterize future targets.

Fresh installation and unrecognized legacy migration run ordinary local proxy ports only. A validated subscription and explicit activation are required for TUN. Once 1.1.2 establishes managed state, subsequent upgrade/reinstall preserves explicit TUN consent and administrative Stop. Legacy migration preserves the subscription URL, full YAML, secret and cron timing, but never inherits transparent enablement.

Use **VPN → Proxy Suite** for service controls, subscription settings and the local merge editor. Runtime state is root-only under `/var/db/os-mihomo/`; static GeoIP data and presets are under `/usr/local/share/mihomo/`. Nothing depends on `/usr/local/etc/mihomo/`, which legacy packages delete asynchronously.

## Configuration

The configuration pipeline is:

```text
complete subscription YAML
  → router DNS overlay, if selected
  → /var/db/os-mihomo/merge.yaml
  → enforced invariants and activation gate
  → mihomo -t validation
  → transactional application
```

Mappings deep-merge; scalars and plain lists replace. Empty mappings clear the existing mapping. `prepend-rules` / `append-rules`, `prepend-proxy-groups` / `append-proxy-groups` and `prepend-proxies` / `append-proxies` extend lists. Appending after a provider `MATCH` rule will not change its priority. No JavaScript/script execution layer is supported.

Three YAML presets are shipped: `full.yaml` (TUN and real-address DNS), `tun-only.yaml` (TUN without Mihomo DNS interception), and `proxy-only.yaml`. Loading a preset replaces the entire merge file; preserve custom content first. The initial merge uses full-mode defaults, with activation gated off. The authenticated dashboard initially binds all interfaces; its settings switch can restrict it to loopback. Default TUN MTU is 1420; adjust it to the smallest effective node transport MTU.

TUN activation with the currently bundled FreeBSD core supports only `gvisor`. Its `system` and `mixed` TCP paths incorrectly classify traffic as broadcast, so the plugin rejects transparent routing with either stack; select gVisor before enabling it. This restriction applies to the bundled core and requires fresh validation for a future core.

The gVisor stack keeps at most 20 KB of each TCP connection in flight, so a single connection runs at about 20 KB per round trip: a few tens of Mbps for a Wi-Fi client even when the rule is `DIRECT`. **Fast TCP path** (off by default) sends new IPv4 TCP from the selected sources to a core listener on `127.0.0.1:7894` through a PF redirect instead, so the kernel's TCP stack carries it; on a test bench a single connection at 18 ms went from 8 Mbps through the TUN to about 1 Gbps. The core still sees the original destination, so rules, the sniffer and node selection are unchanged; its connections show the inbound `opnsense-transparent-tcp` instead of TUN. UDP including QUIC, TCP to port 53 (for the DNS hijack) and IPv6 stay on the TUN. The redirect is used only while the running core owns that listener and the filter has loaded the plugin's `rdr-anchor`; otherwise TCP stays on the TUN, and the status shows why. Stopping the service or losing the core removes the redirect and its connections. Firewall rules see redirected TCP as addressed to `127.0.0.1` port 7894. Rules that block a destination host or port no longer act on captured TCP; pass rules limited to destination hosts or ports no longer match it, so it falls to the default block; a rule blocking access to the firewall itself blocks it. A LAN rule that sets a gateway still matches and routes the redirected connection toward that gateway, where it is lost. Before enabling the fast path, place a rule without a gateway that passes TCP from the captured sources to `127.0.0.1` port 7894 above any such rules, or keep those sources out of capture.

Device policy selects TCP/UDP by LAN source address before traffic enters TUN. A blacklist bypasses the listed sources; a whitelist sends only the listed sources' TCP/UDP through TUN. Off or an empty list sends all eligible LAN sources' TCP/UDP through TUN. ICMP and other control traffic use ordinary routing. Bypassed devices keep their existing routing without using Mihomo's `DIRECT` transport. Traffic selected for TUN then follows subscription and merge rules. Existing firewall pass/block rules and user routing policies still apply. Router-originated traffic and incoming WAN traffic are excluded. With normal stateful firewall/NAT rules, replies for established DNAT connections follow their existing state and correctly configured return routes. Device selection does not restrict clients configured to use HTTP/SOCKS proxy ports explicitly. **Capture interfaces** limits transparent routing to the selected internal interfaces; leaving it empty keeps the earlier behaviour of using every one. An interface counts as WAN-like, and is never captured or offered, when it is the WAN or OPNsense resolves a gateway for it, which covers every uplink of a multi-WAN setup, PPPoE links and VPN exits with a gateway. Select a bridge rather than its member ports, and assign a VPN server's tunnel as an interface before selecting it. The device policy then applies within the selected interfaces, and traffic to any local network still bypasses TUN.

The plugin disables the core's `auto-route` and selects LAN traffic with a separate source policy, avoiding TUN routes that take over public destinations in the normal routing table. Its private routing table retains the system's WAN and VPN routes. Gateway routes explicitly retain their outgoing interface, including WireGuard routes whose gateway is not directly reachable in a fresh routing table. Selection follows IP addresses: use stable addresses or DHCP reservations and cover every address a device actually uses. IPv4 remains the supported client scope; IPv6 needs separate end-to-end validation, and private-jail IPv6 checks do not establish end-to-end client support. Before deployment, exercise blacklist, whitelist, empty lists, user block rules and custom routing policies. The fix still requires acceptance on the target native system.

Multi-WAN DNAT return routing remains administrator-maintained and requires correctly configured system WAN return routes. The plugin does not rewrite NAT, WAN gateways or `reply-to`, and does not repair an existing incorrect return path. Connections requiring a fixed return WAN need the correct stateful WAN rule and `reply-to`. Inline NAT **Pass** skips subsequent filter rules; **Register rule** needs a correctly configured WAN gateway and `reply-to` enabled globally and on the rule for its default return binding. See the official [NAT association](https://docs.opnsense.org/manual/nat.html#filter-rule-association), [WAN reply routing](https://docs.opnsense.org/manual/firewall.html) and [Disable reply-to](https://docs.opnsense.org/manual/firewall_settings.html#disable-reply-to) documentation. Inspect routes, effective PF rules and states, and capture new connections on WAN, LAN and TUN. Existing connections may retain old states after a policy change; remove only affected states if necessary, never the complete state table. Commands and examples are in [DEPLOYMENT.md](../../DEPLOYMENT.md).

Transparent routing requires DNS answers with real addresses. `redir-host` is the default and recommended mode; `normal` is also supported. Devices bypassing TUN cannot rely on Mihomo to handle fake-IP placeholders. Legacy `fake-ip` may remain saved while transparent routing is off. Enabling transparent routing or applying configuration while it is active converts an effective `fake-ip` mode, including a merge override, to `redir-host` and saves that choice in settings. Shared resolvers must also return real addresses. Existing fake-IP caches may need clearing or time to expire.

The device policy and **Capture interfaces** decide where packets go. Who answers the devices that ask the router itself for DNS is a separate setting, the **DNS scope**, described in [Who gets Mihomo DNS](#who-gets-mihomo-dns): all devices, only the devices transparent routing captures, or none.

The code enforces `tun.device: tun_mihomo`, the stored dashboard secret and valid listener ports excluding 53, including extra listeners and the controller. Merge YAML cannot bypass the TUN activation gate or the real-address DNS requirement. The router DNS is integrated with Mihomo DNS only on `127.0.0.1:1053`; custom listeners remain administrator-managed.

## Who gets Mihomo DNS

**DNS scope** (setting `dns_scope`, on the DNS tab beside **Resolve through the router DNS**) decides which devices Mihomo answers when they ask the router itself for DNS. It acts only while transparent routing runs a configuration with the TUN on and Mihomo DNS listening on `127.0.0.1:1053`: the full preset, or a merge YAML that keeps its DNS. The TUN-only preset answers nobody through the router, and the status says so; the proxy-only preset has no transparent routing at all. Whatever the scope, DNS a captured device sends to any other resolver is still answered by Mihomo inside the TUN while **Capture client DNS** is on, and encrypted DNS (DoH, DoT, DoQ) is never redirected.

| Scope | Value | Mihomo answers, when they ask the router DNS | Unbound |
|---|---|---|---|
| All devices | `all` | Every client of the router resolver | Its root is forwarded to Mihomo |
| Only devices captured by transparent routing | `captured` | The IPv4 sources transparent routing captures, asking any IPv4 address of the router, over UDP and TCP | Unchanged |
| No devices | `off` | Nobody | Unchanged |

**Defaults.** An upgrade keeps what the router did before: a settings file without the key reads as `all`, which includes every installation upgraded from the legacy scripts. A fresh installation starts with `captured`, which runs as all devices only while captured devices actually get IPv6 addresses (see the IPv6 paragraph below). Restoring a configuration backup taken before the setting existed keeps the router's current scope, and a `settings/set` API call without `dns_scope` keeps the stored one; the same holds for `ipv6_clients_restricted` (see [IPv6 only for uncaptured devices](#ipv6-only-for-uncaptured-devices)). No other field is kept that way yet, so an API client still posts the full payload it read.

**All devices** is how every earlier release worked. The integration changes the whole resolver, not a per-client path: it turns off **Use System Nameservers** and adds a drop-in forward zone for the root, so every query Unbound does not answer from local data or a more specific forward zone goes to Mihomo. Every client that uses the router for DNS is then answered by Mihomo: devices the policy bypasses, interfaces left out of capture, VPN clients, downstream resolvers such as Pi-hole, and the router itself when its system DNS uses Unbound. When Unbound validates DNSSEC the integration is not applied at all, because Mihomo's answers carry no signatures: Unbound's configuration and upstreams stay exactly as they are, the status shows DNS integration off with the reason, and Mihomo answers only DNS captured in the tunnel. Switching DNSSEC on while the integration is active makes the watchdog return Unbound to its upstreams once; switching it off takes effect when the service next restarts or a change is applied. With router DNS on, Unbound would forward to Mihomo and Mihomo back to Unbound, so all devices counts as off without the stored choice changing; the page greys it out and says why.

**Only devices captured by transparent routing** leaves Unbound alone. For every captured interface with IPv4 sources, the plugin's `mihomo` anchor gets a UDP and a TCP `rdr` sending port 53 from the captured sources to a table of the router's own IPv4 addresses on to `127.0.0.1` port 1053, placed before the fast TCP path's rules. The sources are exactly the ones transparent routing captures: the device policy within **Capture interfaces**, so a blacklist leaves out the listed devices and an empty whitelist takes every device. Every other device, interfaces outside capture, VPN clients on unassigned tunnels, and the router itself keep the router DNS and its AAAA records. The redirect is armed only while the running core owns both the UDP and the TCP listener on that port, the filter has loaded the plugin's `rdr-anchor`, and the watchdog's latest probe of that same core, at most 15 seconds old, found it answering; until then captured devices use the router DNS, and the status shows **Paused** with a note that the redirect is waiting.

The firewall evaluates a redirected query as UDP or TCP to `127.0.0.1` port 1053, and the plugin adds no pass rule that would bypass the administrator's own. The default LAN rule passes it. A rule that passes only DNS to **This Firewall**, a rule that blocks access to the firewall, or a rule with a gateway drops it or sends it to that gateway: place a rule without a gateway that passes TCP and UDP from the captured sources to `127.0.0.1` port 1053 above such rules, or keep that interface out of capture. A port forward of port 53 on a captured interface takes precedence, because the plugin's `rdr-anchor` is evaluated last, and the redirect never sees those queries. The probes run over loopback and cannot see either case; the status hints at it when captured sources have been active for five minutes and none of their DNS has reached Mihomo. Captured devices that use another resolver, such as DoH or a public server handed out by DHCP, raise the same hint, which can then be ignored. A captive portal's rules for unauthenticated clients may likewise stop matching: leave portal interfaces out of capture. CARP and pfsync are not supported with this scope.

Captured devices no longer pass through Unbound, so its blocklists, access lists and per-client statistics do not apply to them, and neither do its local names. With router DNS off, the plugin therefore puts entries at the front of Mihomo's `nameserver-policy` that send the router's own names back to the router DNS, `127.0.0.1` port 53: the system domain; Unbound host overrides and their aliases, by their exact names; the domains Unbound or Dnsmasq forward to other servers; the domains the Dnsmasq, Kea and ISC DHCP servers hand out or register; and the reverse zones of RFC 1918, link-local and unique local addresses and `home.arpa`. Public reverse lookups stay with Mihomo. The names are read whenever the service starts or a change is applied, so a domain added later reaches Mihomo with the next restart. A merge YAML `nameserver-policy` entry for the same key keeps its own value. These entries are never written for all devices, where Unbound forwards to Mihomo and they would loop. If the router DNS does not answer at start, the status says local names cannot resolve until it does. Turning router DNS on as well is the simplest way to keep blocklists and local names: Mihomo then asks the router DNS for everything, captured devices are still answered by Mihomo, and no loop forms.

With Unbound validating DNSSEC, only captured devices is still allowed: Unbound keeps validating for every other device, and the status notes that captured devices asking the router DNS are answered by Mihomo without validation.

The redirect is IPv4 only, like capture. Captured devices that get IPv6 addresses while Mihomo IPv6 is off would receive AAAA records from the router DNS and leave the tunnel over IPv6, so the scope then runs as all devices instead, as earlier releases did, and the status says why; enabling transparent routing never fails over it. They count as getting IPv6 when the router offers it (radvd, automatic RA on track6, a Dnsmasq IPv6 range, Kea DHCPv6 or a DHCPv6 relay) and an interface transparent routing captures holds a global IPv6 address. Link-local, unique local and WAN addresses do not count, so a stock 26.7 installation, whose Dnsmasq IPv6 range hands out nothing until a prefix reaches the LAN, answers only captured devices. A LAN that reaches the Internet over IPv6 without a global address, numbered with unique local addresses behind NPTv6 or IPv6 outbound NAT, or with 6to4 addresses, is not recognised: choose all devices there, or turn on Mihomo IPv6. The watchdog follows changes on its own by restarting the service, which resets proxied connections: to all devices within about 40 seconds of a prefix arriving, back to captured devices at most once every ten minutes. A restart or boot never goes back on its own, so a WAN reconnect before the prefix returns keeps all devices. Each change is logged to `mihomo.log`. While Unbound validates DNSSEC, all devices would answer nobody, so the scope stays at captured devices and the status warns that they can get IPv6 answers from the router DNS over IPv6. None of this happens while [IPv6 only for uncaptured devices](#ipv6-only-for-uncaptured-devices) is on.

Writing or removing the forward zone for all devices restarts Unbound, as in 1.4.x: when the scope is chosen, when only captured devices starts or stops running as all devices because captured devices get IPv6, at start or by the watchdog, and when the service starts or stops, or the watchdog removes the zone after a crash, with all devices in force. The restart takes a few seconds, and a query that arrives meanwhile can go unanswered once, until the client asks again. After each such restart the plugin empties Unbound's cache, whatever **Flush DNS Cache during reload** says, because OPNsense otherwise loads the cache back into the restarted resolver: answers resolved the old way, such as the AAAA records Mihomo withholds, would be served until their TTL ran out, by default at most a day. Names are then resolved afresh as clients ask for them. The setting itself is not changed and still governs every other Unbound restart. If the cache cannot be emptied, `mihomo.log` says so. With **Serve Expired Responses** on and **TTL for Expired Responses** set to 0, which lets Unbound serve expired answers however old, a client can still get the old answer for a name once while Unbound resolves it again.

If anything goes wrong, the redirect is withdrawn and captured devices return to the router DNS, whatever **Restore direct DNS on exit** says; that setting concerns all devices only and is hidden for the other scopes. While only captured devices runs as all devices because captured devices get IPv6, a crash returns Unbound to its own upstreams whatever the setting says, too. Every few seconds the watchdog asks Mihomo `localhost`, which it answers without any upstream; an armed core that does not answer is asked again a second later, and a second failure withdraws the redirect. That query needs NOERROR or NXDOMAIN; any other answer, REFUSED included, counts as a failure. About once a minute the watchdog also asks a random name under example.com, cloudflare.com or microsoft.com, asking the router DNS the same name only when Mihomo fails. There NXDOMAIN and an empty answer count as success, only a timeout or SERVFAIL counts as failure, and any other answer proves nothing. A wrong verdict can only hand captured devices to the router DNS for a while. Withdrawing drops the redirected states, which covers any the administrator's own port forward to `127.0.0.1` port 1053 created; arming drops earlier states of captured sources to the router's port 53, so a forwarder with a fixed source port moves over at once.

| Failure (only captured devices) | Captured devices | Recovery |
|---|---|---|
| The core crashes | The next watchdog tick withdraws the redirect with capture and drops its states | About 5 seconds; the watchdog restarts the core 10 seconds later, which arms the redirect again (see [Automatic restart, memory and logs](#automatic-restart-memory-and-logs)) |
| The core stops answering DNS | Queries to the router time out until the next liveness probe and the one a second after it both fail, then the redirect is withdrawn | About 10 seconds, at most about 15 on a busy router; re-armed after three passing probes, about 15 seconds later |
| Mihomo's upstreams fail while the router DNS resolves | SERVFAIL or no answer until names under two different probe zones fail through Mihomo and resolve through the router DNS; then withdrawn | About 1 to 2 minutes; re-armed once Mihomo resolves a probe name again |
| The WAN is down, so both fail | Nothing is withdrawn; they fail like every other device | With the WAN |
| The listener is missing, taken, or bound on one transport only | Never armed, or withdrawn | Within one watchdog tick |
| A rule the plugin did not write appears in its anchor | Enable, refresh and disable fail closed and empty the anchor's source and router-address tables: capture and the redirect stop, DNS goes to the router | Remove the foreign rule |
| A filter rule, a gateway rule or a port forward takes the query | Dropped, or answered by the port forward's target; the status hints at it | Fix the rule, leave the interface out of capture, or change the scope |
| Unbound stops | With router DNS off, still answered by Mihomo, except local names; with router DNS on, Mihomo asks Unbound, so they lose DNS like the other devices | With Unbound; other devices lose DNS as they always did |
| The watchdog itself exits | Nothing later is withdrawn or restarted; the status turns stale after 20 seconds | Start or stop the service |
| Stop, apply, a settings or scope change | Withdrawn with its states before the core stops | Immediately |
| Package upgrade | The old package's suspend withdraws it | The new package's boot re-arms it |
| Reboot | Nothing survives: the rules exist only in the running firewall | After the boot start |

| Failure (all devices) | Every device using the router DNS | Recovery |
|---|---|---|
| Unbound validates DNSSEC | Not integrated; Unbound unchanged, the status says why | Not applicable |
| The core crashes, **Restore direct DNS on exit** on | `forward-first` lets Unbound resolve on its own; the watchdog then removes the zone | About 5 seconds plus an Unbound restart; the core and its zone return with the automatic restart 10 seconds later |
| The core crashes, **Restore direct DNS on exit** off | Unbound keeps forwarding to the stopped core, and the names it forwards fail; a stored only captured devices running as all devices is restored as if the setting were on | With the automatic restart 10 seconds after the watchdog noticed the exit, or by hand once it is paused |
| Boot | See [Recovery and subscriptions](#recovery-and-subscriptions) | Once the boot start restores direct DNS |

Downgrading to 1.4.x withdraws the redirect when the old package suspends the service, and 1.4.x then answers every device through Mihomo again whenever router DNS is off and the full preset is in use.

## Resolve through router DNS

This switch defaults off. It supplies exactly these DNS keys before the local merge:

```yaml
dns:
  nameserver: [127.0.0.1]
  proxy-server-nameserver: [127.0.0.1]
  default-nameserver: [127.0.0.1]
  nameserver-policy: {}
```

The switch itself leaves `dns-hijack` and Unbound AAAA policy unchanged; transparent routing separately enforces real-address DNS. Other merge overrides remain explicit administrator choices. Provider fallback servers must be removed before activation; an unavailable local resolver fails startup rather than reverting to provider DNS. Unbound is never forwarded back into Mihomo while this switch is selected: a DNS scope of all devices counts as off, so every device that is not captured keeps Unbound's upstreams. Only captured devices still works with it and is the recommended pairing: captured devices are answered by Mihomo, which asks the router DNS with its local names and blocklists.

Manual DNS fields accept Mihomo URLs. The **Override subscription DNS** switch controls whether their nonempty values replace the matching fields in the generated runtime configuration; switching it off keeps the values for later use and restores subscription DNS immediately. The stored subscription YAML is never rewritten, and router DNS takes priority while selected. Mihomo uses the first token after `#` as a proxy or interface, while Unbound uses `IP@port#hostname` for a TLS verification name. To keep copied Unbound endpoints from failing later with `interface not found`, the plugin normalizes `tls://IP#long.hostname` in Nameservers and Proxy node servers to `tls://long.hostname`; short interface selectors such as `#vtnet1` and `#RULES` remain unchanged. Bootstrap servers still require a literal IP, so the same copied form is stored there as its IP endpoint and the normalized hostname field performs the encrypted queries without a dependency loop.

IPv4 and IPv6 forwarding addresses are read from the router's generated DoT configuration; saved ownership state recovers original upstreams during a transition out of Mihomo DNS forwarding. Host routes and `DST-PORT,853,DIRECT` precede subscription and merge rules. The watchdog refreshes them when upstream addresses change. This avoids routing Unbound's own DNS transport through a node whose hostname it must resolve.

Startup records a local fingerprint of system DNS written by the core. After a crash, native OPNsense DNS regeneration restores system resolution and retries on failure. Later operator edits or explicitly configured DNS are preserved. This temporary recovery record is excluded from XML backups.

The current supported deployment scope is IPv4 clients. When resolve-through-router-DNS is selected, RA or DHCPv6 advertisement with disabled Mihomo IPv6 causes activation refusal and a visible runtime warning if enabled later, unless [IPv6 only for uncaptured devices](#ipv6-only-for-uncaptured-devices) is on. With router DNS selected, the plugin does not suppress AAAA. With router DNS off and the DNS scope at all devices, Mihomo answers according to its IPv6 switch, which defaults off, so no client that uses the router for DNS receives AAAA records for the names Unbound forwards to Mihomo, including clients that are not captured. With only captured devices, Mihomo answers just those devices' IPv4 queries to the router, and while captured devices get IPv6 addresses that Mihomo does not carry the scope runs as all devices (see [Who gets Mihomo DNS](#who-gets-mihomo-dns)). The plugin never configures RA/DHCPv6. With Mihomo IPv6 disabled, native IPv6 traffic bypasses TUN. Validate IPv6 end to end before enabling IPv6 proxying for clients.

## IPv6 only for uncaptured devices

**IPv6 only for uncaptured devices** (setting `ipv6_clients_restricted`, on the DNS tab below **DNS scope**, off by default) is the administrator's promise that this router gives IPv6 only to chosen devices transparent routing does not capture, such as a NAS that must be reachable over IPv6, and none to captured devices. The plugin does not check it. While it is on and Mihomo IPv6 is off, an IPv6 offer no longer stops router DNS at activation or raises the watchdog's runtime error, and the scope only devices captured by transparent routing no longer falls back to all devices: the watchdog neither looks at the interfaces nor restarts the service for it. Detection itself is unchanged, and the status notes that an offer was found and allowed by the declaration. Off, everything behaves exactly as without the setting. With Mihomo IPv6 on it changes nothing. An upgrade, a backup restore without the key and a `settings/set` call without it keep the stored value; nothing stored means off.

**Risk.** The promise is all that keeps captured devices off IPv6. A captured device that gets a global IPv6 address anyway can reach IPv6 destinations outside the tunnel and get AAAA records from the router DNS over IPv6, bypassing the proxy.

**DNS scope.** The declaration fits router DNS, or the scope only captured devices or no devices. With all devices and router DNS off, Mihomo answers every device with its IPv6 switch off, so the devices given IPv6 get no AAAA records from the router DNS either and connect out by name over IPv4 only; the page warns beside the switch and the status says so.

**Recommended OPNsense 26.7 setup**, for one NAS on a LAN that tracks a prefix the ISP delegates by DHCPv6-PD:

1. Keep the NAS out of capture: blacklist it, leave it out of a whitelist, or put it on an interface outside **Capture interfaces**.
2. Under **Services > Router Advertisements**, add an entry for the LAN in **Managed** mode, so devices get addresses only from DHCPv6 and none by SLAAC, and clear its advanced **Enable DNS** option, so no device is told of an IPv6 resolver; the NAS still gets AAAA records from the router DNS over IPv4. The entry replaces the automatic advertisements of a tracking LAN, which, like Assisted, Stateless and Unmanaged, let every device configure an address itself.
3. In Dnsmasq, delete every other IPv6 range on the interfaces transparent routing captures, including the stock `::1000` to `::2000` range in `slaac` mode, and turn off the general **Router advertisements** switch, so the Managed entry is the only RA source. Then add one IPv6 range on the LAN with the constructor set to the LAN and mode **Static**, which serves only reservations, and no RA mode; reserve the NAS's MAC address with its suffix, for example `::4`. No Kea or ISC DHCPv6 service may serve those interfaces either.
4. Pass IPv6 on the LAN only from that host, for example with a Dynamic IPv6 Host alias of the LAN prefix and the same suffix, which follows a prefix change, and block all other IPv6 arriving on the LAN, from any source address and to the firewall's own addresses too; OPNsense's automatic rules for neighbour discovery and DHCPv6 still apply first.

Devices without a reservation then get no IPv6 address to use and no IPv6 path to the router DNS. The plugin never configures RA, DHCPv6 or firewall rules itself.

## Recovery and subscriptions

Every core crash removes the plugin's transparent capture policy and TUN routes, and with them the captured-device DNS redirect. Automatic restoration of original Unbound DNS, which only the all-devices scope needs, is enabled by default and configurable per router. Disabling DNS recovery leaves proxy DNS forwarding in place after a crash, while capture is still removed. Explicit Stop always stops the core and removes transparent capture even if DNS restoration fails; its pending restoration is retried, and neither a WAN event nor the watchdog revives an administratively stopped service. A core that exits without a Stop is started again by the watchdog, as described next. The service starts at boot unless it was stopped; OPNsense never runs `rc.d/mihomo` itself, so a start hook does it. Shutdown does not stop the core, so an active all-devices DNS integration survives a reboot and Unbound forwards to a listener that is not up yet until that hook runs (the captured-device redirect lives only in the running firewall and does not survive); the boot start restores direct DNS before it renders or validates the configuration, which leaves a window of a few seconds after Unbound starts. In that window the names Unbound forwards fail to resolve when DNS recovery is off; with it on, Unbound falls back to resolving them itself. Only address changes on WAN-like interfaces restart the core, and IPv6 renewals are ignored while Mihomo IPv6 is off, so DHCPv6 renewals no longer reset proxied connections. Disabling removes only plugin-created interfaces, policies and routes, without flushing the firewall state table.

Subscriptions are fetched directly with `OPNsense-Mihomo/1 (device)`. HTTP 4xx never retry or use fallback; only timeout/5xx permit at most two direct and two proxy attempts. The URL stays in a private curl file, outside command arguments and logs. The UI does not send the stored URL back as HTML. Updates preserve proxy/group/rule semantics and dashboard credentials. CLI `/usr/bin/mihomo_sub`, configd and cron use the same manager.

## Automatic restart, memory and logs

When the core exits without a Stop, because it crashed or because the kernel killed it when the router ran out of memory, the watchdog first rescues routing and DNS as described above. Once that has succeeded it starts the core again through the same path as the **Start** button, so transparent routing, the fast TCP path and the DNS scope with its forward zone or redirect come back exactly as after a manual start. The first automatic restart follows 10 seconds after the watchdog noticed the exit, a second one in a row 60 seconds after, any later one 300 seconds after; a start that fails counts as one and is retried on the same ladder. At most three automatic restarts happen within any 60 minutes. After that the watchdog stops trying, and the status error says `Mihomo exited repeatedly; automatic restart is paused after 3 restarts within an hour. Start resumes it.` `mihomo.log` records the pause beside what met it, for example `Mihomo stopped (exited unexpectedly); automatic restart is paused after 3 restarts within an hour. Start resumes it.` **Start**, **Restart** and **Stop** each reset the count.

Nothing is restarted after Stop, after the stop of a package upgrade or removal, while Sing-box owns transparent routing, or after a DNS scope change whose rollback left the service stopped. A restart that fails after a WAN address change, after a subscription update, scheduled or not, or when the watchdog re-applies the configuration for new router DNS upstreams leaves the core down without anyone having asked for that, so it is retried like an exit, on the same ladder and within the same three an hour. A **Start**, **Restart** or settings change of your own that fails is reported to you and not retried.

While a restored configuration backup is pending, or the saved backup was edited and waits for its repair, the watchdog only rescues routing and DNS: it neither restarts the core nor guards its memory until **Stop**, the restore or repair, or a reboot. A restart that is due waits, and so does one while the routing cleanup after an exit keeps failing; the status then says the restart waits for the problem it reports instead of naming a time.

The watchdog looks up the exited core's PID in the kernel message buffer (`dmesg`), counting only a line written after that core started, since the buffer keeps lines for days and PIDs come round again within hours. When the kernel killed it, the log and the status say so, for example `killed by the kernel: failed to reclaim memory`; otherwise they say `exited unexpectedly`. Every exit, scheduled restart, attempt, failure and pause is logged to `mihomo.log`. Beside the service state, the status shows when and why the watchdog last restarted the core, until the next Start, Restart or Stop. The count is kept in `/var/run/mihomo-restart.json`; a reboot clears it and starts the core anyway.

**Memory.** The core starts with Go's soft memory limit, `GOMEMLIMIT`, set to 30% of physical memory (`hw.physmem`) and never below 256 MiB, so its garbage collector works harder before the core grows into the rest of the router's memory. The watchdog also reads the core's resident memory on every tick, except while a backup is pending as described above. Above half of physical memory it logs that and restarts the core in a controlled way, counted against the same three restarts an hour and spaced like them: a core that is above the limit again soon after an automatic restart waits until 60 seconds after it, and after a second until 300 seconds after that. This happens before the kernel has to kill a process for memory. The status shows the core's memory and that limit, for example `Core memory: 171 MB (restarted above 2.0 GB)`. A core that really needs more than half of the router's memory is restarted until the budget is spent and then left running, with the status error `Mihomo went above its memory restart limit again; automatic restart is paused after 3 restarts within an hour. Start resumes it.` Give the router more memory, or reduce the subscription's rules and providers.

**Logs.** The core and the watchdog write `/var/log/mihomo.log` through daemon(8) supervisors, which keep the file open. They now run with `-H`, and when newsyslog rotates the file (at 1 MB, five kept) it runs `/usr/local/opnsense/scripts/mihomo/reopen_log.sh`. That sends SIGHUP to each supervisor this release recorded as started with `-H` and proves to be the one running, and both reopen the new file. In earlier releases both went on writing into the rotated file, and every line after the first rotation was lost. A supervisor started by an older release is left alone, because SIGHUP would end it; the upgrade restarts both. `mihomo_sub.log` is opened for every line and rotates without help.

## Build and publish

Run `sh build.sh` on the recipe's native FreeBSD / OPNsense target with matching Python, PyYAML and curl. Current 26.7 uses `python3.13` / `python313` and produces `dist/FreeBSD:15:amd64/os-mihomo-1.5.1.pkg`. `TARGET_ABI`, `TARGET_PRODUCT_ABI` and `TARGET_PYTHON` can be explicit; the actual kernel, userland, dependencies and interpreter must match. Runtime Python entry points and product annotations follow the target. Bytecode is excluded and rejected in staging and archives. See [deployment](../../DEPLOYMENT.md) for per-target native tests, signed dependency setup and publication. Pages reruns the signed report's source tests and compares package content with that revision.
